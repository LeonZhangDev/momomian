这题在问什么

考查谁决定下一步，以及这种自由度是否值得。这里把 Agent 理解为模型能够在约束内选择动作的系统。

简答版

固定工作流通常由代码预先规定执行路径；Agent 可以根据当前状态和工具返回选择后续动作。两者都可以调用模型和工具。问题是决策范围是否需要开放：路径清楚、规则稳定时，普通代码往往更容易测试；任务需要根据新信息调整计划时，再考虑 Agent，并给它明确的权限、预算和停止条件。

必答点

  • 决策范围：比较路径主要由代码预设，还是允许模型根据状态选择。
  • 观察反馈：工具返回应影响下一步；仅生成一段计划不等于已经执行任务。
  • 可控性与代价：自由度会增加测试、延迟与成本，需要有边界。
展开详细解析：为什么这样回答

先看需求

每天把固定三列 CSV 汇总成报表，规则确定，普通函数或定时流程就足够。若任务是调查一个未知问题，检索结果可能要求换关键词或补查来源，开放决策更有价值。

再看执行链

一个最小闭环是读取状态、选择动作、验证并执行、接收观察、决定继续或结束。任何一步失败都要有可见结果，不能把模型提出动作当作动作成功。

最后说明边界

实际系统可以混合两者，例如代码固定审批和写入边界，模型只决定检索查询。Agent 自由度越大，不代表任务质量必然更高。

把答案放进一个具体场景

做一个“查资料后整理报价”的助手。固定每天汇总价格，和根据查到的信息决定补查哪些商品，是两种不同的决策需求。

  1. 先说明固定汇总可用代码直接完成；需要根据观察调整查询时，才给模型开放查询决策。
  2. 模型只能提出允许的动作，应用负责参数、权限和执行；工具观察返回后才能改变下一轮状态。
  3. 写清最大步数、结束条件和人工接管出口，再拿相同任务比较质量、延迟与成本。

为什么这样答不够：“用了LLM就是Agent”没有解释谁决定下一步，也没有说明引入循环的收益。

这题在问什么

考查文本怎样被编码，以及请求预算怎样核对；不要求背一个“汉字换算系数”。

简答版

Token 是特定分词器编码文本得到的单位，同样的汉字、英文、标点或空白可能被拆成不同数量。统计要绑定模型及其分词规则，并同时考虑输入、输出和服务端附加格式。开发时可用对应 tokenizer 做估算，实际计费和用量再核对服务返回，不能直接把字数当 Token 数。

必答点

  • 分词器与文本：编码规则和文本内容共同影响数量，字数与 Token 数没有固定一比一关系。
  • 输入与输出预算：预留输出及服务格式开销，不能把窗口全塞满。
  • 核对适用模型：其他模型的编码实验不能直接代表目标服务的用量。
展开详细解析：为什么这样回答

从编码理解差异

一个常见词可能对应一个单位，一个少见字符串可能拆成多个单位。空白、符号和多字节文本也参与编码，所以两段等长文字不一定有相同 Token 数。

从请求核对预算

把消息正文、系统说明和工具定义按目标接口的计数方式处理，再为输出留余量。只编码一段正文通常没有覆盖完整聊天请求。

从结果校准估算

本站真实编码实验使用 o200k_base 或 cl100k_base，能观察 Token ID 与往返。接入其他模型前仍需核对官方规则或服务返回；这里不提供百炼用量的固定换算。

把答案放进一个具体场景

窗口上限是假设的1000单位：当前输入估算850，计划最多输出300。即使用户文字很短，也可能超过整体预算。

  1. 先分开输入估算、预留输出与服务格式开销，850+300已经超过示例窗口。
  2. 确定目标模型和分词器再计数，消息角色、工具定义等也可能占输入；其他分词器只作观察。
  3. 实际调用后核对usage及服务限制；生产策略用真实样本评估裁剪对任务质量的影响。

为什么这样答不够：“一个汉字等于一个Token”会同时误算中文、代码、标点和附加格式。

这题在问什么

考查可解析、符合结构与满足业务规则之间的区别。

简答版

合法 JSON 只说明文本可解析。随后还要检查字段、类型和约束，再检查业务含义与授权。例如姓名是空字符串、日期已过期、价格为负数，都可能是合法 JSON，却不满足业务规则。校验失败应返回可定位的错误，并限制修正次数；不能静默改成另一个业务请求。

必答点

  • 分层校验：依次检查语法、结构、业务规则与权限。
  • 失败可观察：指出哪个字段、违反什么条件，避免只返回“失败”。
  • 受控修正：允许补充或重试时设置次数边界，不能跳过校验执行。
展开详细解析：为什么这样回答

结构只解决一层问题

价格字段为数字可以满足类型约束，但价格是否允许为零或负数由业务决定；日期字符串可解析，也不代表仍在预约窗口内。

把错误变成输入

校验器可以返回字段和错误码，调用方再请求用户补充信息，或让模型只修正被指出的字段。修正后必须重新经过相同校验器。

保留失败路径

重复修正仍不合法时停止并说明原因。日志记录必要的字段与错误，不应把密钥或不必要的个人信息直接打印进去。

把答案放进一个具体场景

服务返回 {"people": -2}，可以解析且people是整数，但预约人数不能为负。

  1. 先判断传输及返回状态，再判断文本能否解析成JSON。
  2. 对照Schema检查必填字段、类型和额外字段；业务规则再检查人数范围、日期和授权。
  3. 失败后给出可定位的错误；受限修复仍要重新校验，不能只把字符串“修成JSON”就执行。

为什么这样答不够：“能json.loads就安全”跳过结构与业务规则，也无法防止越权。

这题在问什么

考查是否需要开放该能力，以及执行端怎样约束调用。

简答版

当能力无法定义清楚的输入输出、缺少授权边界，或副作用无法控制时，我不会直接把它开放给模型。只开放完成任务需要的最小能力，执行端校验参数、身份与资源范围。只读查询也可能泄露数据；高风险写入还要核对当前意图、展示将发生的操作，并按产品规则要求确认与回执。

必答点

  • 最小权限：开放具体动作与资源范围，避免任意 SQL、命令或文件访问。
  • 执行端授权：模型选择了工具，不代表用户有权执行。
  • 副作用边界：写入前检查必要确认，写入后核对真实结果。
展开详细解析：为什么这样回答

先缩小能力

查询订单状态比“执行任意数据库语句”更容易定义输入、访问范围与失败返回。能用普通函数固定处理的内部步骤，不必全部暴露给模型。

再区分风险

只读工具主要关注数据范围、隐私、限流和成本。付款、删除、预约等写入还关注重复执行、审批有效期和撤销可能性。

最后验证拒绝

测试越权资源、缺参数、过期授权和恶意文本。提示词中写“请谨慎”不能替代执行端检查。

把答案放进一个具体场景

模型建议调用天气工具，参数为北京；它随后在文本里说“查询成功”，但应用还没执行。

  1. 先识别工具请求不是结果，验证工具在允许列表且参数满足契约。
  2. 实际执行后按调用ID回填返回值或错误；同时有多个调用时不能只按工具名匹配。
  3. 下一轮以真实观察组织回答，若结果缺失就明确未完成，不让模型文字替代执行证据。

为什么这样答不够：“模型选择了正确工具，所以调用已成功”把建议、执行和结果混成一步。

这题在问什么

考查调用方未知状态与业务执行状态的区别。查询和幂等均取决于服务实际支持。

简答版

超时只说明没有及时拿到响应，预约可能未执行，也可能已提交而响应丢失。我会保留原请求标识，若服务支持查询就先核对结果；确需重试时，按服务约定复用幂等键，并设置有限次数和退出条件。没有查询或服务端幂等支持时，不能宣称安全重放，应保留未知状态并转核对流程。

必答点

  • 超时表示结果未知：不能直接推断业务成功或失败。
  • 先核对执行结果：服务支持按请求 ID 查询时，先补足证据。
  • 服务端幂等支持：客户端生成键本身不能阻止服务端重复写入。
  • 有限重试与退出：日志保留原标识与未知状态，无法确认时停止自动重放。
展开详细解析：为什么这样回答

比较两条时序

路径一是请求尚未到达服务就超时；路径二是服务已经写入，但返回在网络中丢失。调用方可能在两条路径中收到完全相同的超时。

查询与幂等各做一件事

查询补足已发生什么的证据，幂等约定控制重复请求的效果。确认原请求成功就返回回执；确认未执行且允许重试，再按原约定提交。

不要越过未知

若查询仍是处理中或无法查询，应按服务规则等待、退出或人工核对。换新请求 ID 可能绕开原来的去重保护。

把答案放进一个具体场景

创建预约后等待超时，用户没有看到响应；服务端是否写入仍未知。

  1. 先区分请求根本没发送、明确拒绝和发送后结果未知，处理策略不同。
  2. 未知结果优先按幂等键查状态或恢复结果；临时错误的有限退避要受总超时和次数限制。
  3. 给用户说明当前未知和下一步，记录请求ID、重试次数、阶段耗时，便于复现与排查。

为什么这样答不够：“所有超时重试三次”可能生成多个预约，而且三次并不是通用策略。

用代码检验理解

  • 有限重试的判断
  • 同一请求只执行一次

常见误区

“重试三次所以安全”只限制次数，没有解决重复副作用；“换个键再试”可能创建第二个预约。

追问怎么接

简答版

必答点

  • 能力发现与调用协议：工具有名称与输入约定，客户端可以列出和调用。
  • 业务语义与授权：协议连接成功不等于用户有权完成所有操作。

统一连接方式

工具服务声明能力，客户端使用协议列举工具并提交参数。这减少逐个服务自创调用格式的适配工作。

应用仍需做判断

例如查询订单工具的 schema 要求 order_id，但执行端仍要确认该订单属于当前用户。合法参数只能说明格式符合约定。

返回也需解释

调用可能在协议层失败，也可能成功返回一个工具执行错误。应用要记录可见错误并决定退出或修正，不能把“收到了消息”视为业务完成。

这题在问什么

考查从题目约束推导算法，再判断工程变式是否仍满足这些约束。

简答版

先明确输入、目标、约束和边界，再给出正确性依据与时间、空间复杂度。工程迁移要重新检查目标：高频 Top-k 先统计频次，相似度 Top-k 按已有分数选候选，上下文选择还受预算、依赖与证据完整性约束。可以复用数据结构，不能把同一个排序代码当作三种任务的完整答案。

必答点

  • 约束与目标：先定义按什么选、是否保序、如何处理同分及空输入。
  • 正确性与复杂度：说明不变量与 n、k 的范围，复杂度对应具体实现。
  • 工程额外边界：加入资源、并发、版本和业务正确性后重新验证。
展开详细解析：为什么这样回答

以分数 Top-k 为例

设 n 个有限可比较分数、0<k≤n，固定容量小顶堆保留当前最高 k 项；堆满后只在新分数超过最小项时替换。处理了长度为 t 的前缀后，堆保留该前缀的最高 min(k,t) 项，这是正确性依据。同分规则要另行定义。

计算实际复杂度

k≥2 时，维护 k 项堆需 O(n log k) 时间、O(k) 额外空间，若输出还要排序需 O(k log k)。k=1 可用 O(n) 扫描，不能把 log 1 为零代入后忽略读取输入的时间。全量排序通常 O(n log n)，本站允许排序的短题不应被描述成已经用了堆。k≤0 返回空，k>n 与空输入按约定处理。

再回到工程目标

高频任务还需频次计数；相似度分数不是事实概率；上下文预算需要同时保护必要条件与工具配对，按最高分直接装满可能破坏完整性。为变化后的约束添加测试。

  2. 先写正确的字典+列表版本并解释单次最坏O(c)，再讨论哈希表与双向链表的平均O(1)。
  3. 补更新已有键、未命中、容量1和空操作测试；清楚地区分本机测试通过与真实并发缓存。
