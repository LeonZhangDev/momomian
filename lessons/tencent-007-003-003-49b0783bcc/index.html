跟着一组输入，学完这一步

同一任务的四种事件，各显示什么

  • 区分完整状态、节点更新、模型片段和自定义进度
  • 区分中间文字出现与最终完成
  • 断流或取消后保留草稿，不宣称任务成功
卡住时，先补哪一小节？
  • 先知道状态和局部更新

不要把所有事件都拼进回答

values 表示状态视图，updates 表示节点更新，messages 用于模型消息增量，custom 是应用主动发送的进度等信息。本课沿用站内已经验证的 stream-mode 思路，不要求换用最新接口；具体事件外形要看框架版本和所选模式。

给同一任务设不同显示位置

“找到两份资料”适合进度行，不能混成回答的一部分。模型逐字输出进入回答草稿；节点结束时的证据列表用于检查来源；最终图结束和业务回执则决定任务是否完成。一个画面可以展示这些信息，但应给它们各自的状态。

传输结束未必等于业务完成

连接关闭可能是正常结束，也可能是用户取消或网络中断。若尚无终态，界面应显示“未完成，可恢复”，保留已收到的草稿。重连需要知道是否支持事件编号和重放，不能随意重复追加文字，更不能把半份工具参数拿去执行。

把输入代进去，走一遍

以下是本站固定教学样例，用来观察规则，不是线上服务的测量结果。

教学资料任务 q1：检索两块 refund-v2#3、#4；模型生成“可在7天内申请”；事件序号是本例应用约定，不宣称所有框架事件天然有同一序号字段。

步骤当前内容或状态为什么这样变化
初始状态values → question=q1；evidence=[]；answer=空给调试或状态视图使用，不把整份对象当成最终回答。
检索完成updates → retrieve:{evidence:[#3,#4]}；custom → 找到2块节点更新改变状态；进度消息进入状态提示行。
逐片生成messages → “可在” → “7天内” → “申请”按当前消息和运行标识追加到回答草稿，保留归属边界。
结束核对最终状态 answer=可在7天内申请；run=completed本题假定收到明确完成状态，才把草稿标为完成。若此信号未到，不能照搬这个结论。

最后得到：进度行、状态视图和回答草稿分开。文字已显示只能证明收到了一些输出，不能证明后续引用、工具动作和业务任务完成。

如果这一步出错呢？

触发条件：在“可在7天”之后断流，却显示“全部完成”；或重连后把旧片段再拼一次。

消息片段到达 → 连接断开 → 未观察到完成状态 → 草稿只有“可在7天”，任务结果不完整。

恢复方法：保留草稿并显示中断状态。按该服务实际支持的运行查询或事件恢复机制核对；支持去重时使用明确事件 ID，不支持时重新取权威状态，不盲目拼接。

先口述、画两行状态或改一个值即可。检查方法在提交小测后也可以回来核对。

想完后，对照检查方向

  • 不把取消等同于外部副作用已撤销

原讲解与示例

流式传输

LangGraph 实现了流式处理系统，以提供实时更新。流式处理对于提升基于 LLM 构建的应用程序的响应能力至关重要。通过逐步显示输出，甚至在完整响应准备就绪之前，流式处理能显著改善用户体验，尤其是在处理 LLM 的延迟时。

LangGraph 流式处理可实现的功能：

  • 流式传输图状态 — 通过 updates 和 values 模式获取状态更新/值。
  • 流式传输子图输出 — 包含父图和任何嵌套子图的输出。
  • 流式传输 LLM 令牌 — 从节点、子图或工具内部捕获令牌流。
  • 流式传输自定义数据 — 直接从工具函数发送自定义更新或进度信号。
  • 使用多种流模式 — 从 values（完整状态）、updates（状态增量）、messages（LLM 令牌 + 元数据）、custom（任意用户数据）或 debug（详细跟踪）中选择。

支持的流模式

将一个或多个以下流模式作为列表传递给stream或astream方法：

模式

描述

values

在图执行的每一步之后流式传输状态的完整值。

updates

在图执行的每一步之后流式传输状态的更新。如果在同一步骤中进行了多次更新（例如，运行了多个节点），这些更新将分别流式传输。

custom

从图节点内部流式传输自定义数据。

messages

从任何调用 LLM 的图节点流式传输 2 元组（LLM 令牌，元数据）。

debug

在图执行过程中流式传输尽可能多的信息。
