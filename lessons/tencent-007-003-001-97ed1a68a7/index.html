保存器不都能跨进程

内存保存器适合演示会话隔离和读取检查点，进程结束后不能据此保证恢复。需要跨进程时，应使用真正的持久化后端，并确认存储路径、连接参数和保存提交已经完成。仅在代码旁写“可以重启”不算完成重启实验。

把重启拆成可观察的两段

下面演练用“进程 A 写入并关闭；进程 B 打开同一存储并读取”的验收顺序。表中的记录为固定教学数据；旁边已有 LangGraph 配套验证的是其列出的实际断言，不能把本表当成对新保存器的运行报告。

保存任务状态不能包办业务事务

检查点保存内部状态，外部预约可能发生在另一个服务。外部写入成功、内部状态还没保存时崩溃，恢复后会出现“内部不知道，但外部已执行”的空隙。稳定业务请求键和查询回执仍然必要。

以下是本站固定教学样例，用来观察规则，不是线上服务的测量结果。

教学存储 path=同一个持久化后端；thread=t8 属于 u7。进程 A 将 evidence=[refund-v2#3]、next=answer 保存为 checkpoint=c2，然后正常关闭。

步骤当前内容或状态为什么这样变化
进程 A 写入thread=t8；checkpoint=c2；next=answer必须确认后端真正接受保存，而不是仅给一个内存变量赋值。
进程 A 退出A 的内存对象消失；持久化记录 c2 留在后端这一步区分跨进程存储和内存保存器。
进程 B 重新连接核验 u7 可读 t8；使用同一后端读取 c2路径或命名空间不同会形成另一份存储；ID 相同不够。
从保存状态继续evidence=[refund-v2#3]；执行 answer；记录新 checkpoint继续的位置由保存状态和图版本决定，不是从 Python 函数的任意机器指令继续。

最后得到：能够区分“内存里读回一次”和“关闭原进程后读取同一后端”两种证据。恢复还需核对图版本、权限和外部动作。

如果这一步出错呢？

触发条件：仅用 InMemorySaver，却以为只要 thread_id 不变就能重启恢复。

A 写内存检查点 → A 结束 → B 新建内存保存器 → thread=t8 查不到 A 的数据。

恢复方法：选择受支持的持久化保存器，记录后端、会话标识和版本。按两进程顺序验证；若外部动作状态未知，先查询业务回执，再决定如何继续。

持久化

LangGraph 内置了一个通过检查点器实现的持久化层。当你使用检查点器编译图时，检查点器会在每个超级步骤保存图状态的检查点。这些检查点被保存到一个线程中，可以在图执行后访问。因为线程允许在执行后访问图的状态，所以包括人在回路、记忆、时间旅行和容错在内的几个强大功能都成为可能。下面，我们将更详细地讨论这些概念。

Agent Server 自动处理检查点 当使用 Agent Server 时，你不需要手动实现或配置检查点器。服务器会在幕后为你处理所有的持久化基础设施。

线程

更正：线程是由thread_id标识的状态历史容器，包含一系列运行和检查点；每个检查点另有checkpoint_id。

查看解释与参考资料

一个线程包含多个检查点；thread_id定位线程，checkpoint_id定位线程内的快照。

线程是检查点器为每个保存的检查点分配的唯一 ID 或线程标识符。它包含一系列运行的累积状态。当运行被执行时，助手底层图的状态将被持久化到线程中。

当使用检查点器调用图时，你必须在配置的可配置部分指定一个thread_id：

{"configurable": {"thread_id": "1"}}

更正：使用Agent Server线程API时按其接口创建线程；本地检查点图通常直接传入thread_id运行，无需额外线程创建请求。

查看解释与参考资料

预先调用线程创建API属于Agent Server用法；本地编译图一般可直接用thread_id调用。

可以检索线程的当前和历史状态。为了持久化状态，必须在执行运行之前创建线程。LangSmith API 提供了几个用于创建和管理线程及线程状态的端点。更多详情请参阅 API 参考。

检查点器使用thread_id作为存储和检索检查点的主键。没有它，检查点器无法保存状态或在中断后恢复执行，因为检查点器使用thread_id来加载保存的状态。
