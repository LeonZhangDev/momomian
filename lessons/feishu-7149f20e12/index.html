本课召回内容上下文扩充，解决什么矛盾？ 结论：短块便于定位，生成回答可能需要相邻更完整上下文。 理由：短文本可提高检索聚焦程度，命中后再补前后段或父级内容，这样将定位与回答依据分开设计，避免为了上下文完整而一味增大所有向量块。 配套示例：命中“报销上限”段后一并取回前段适用人员条件，再交模型作答。 本课多Agent敏感状态传递，哪种设计最符合其建议？ 结论：按Schema传必要字段，私有记忆分角色限制。 理由：协作不等于共享全部信息，显式字段约束减少意外暴露，角色记忆与外部服务边界限制谁能读取什么，应在执行层落实而非只写一句保密。 配套示例：预约Agent只收到所需空档与用户偏好，不接收无关支付凭据。

网龙的面试只有一面，这一面是两个面试官一起问的。问的问题是目前我接触到面试面的最细的，他基本上是问到底，一般面试都是让你讲一下大概的方法是啥，这次面试面试官基本上要问到底，不光问用什么方法，还问怎么用的，甚至还问这个方法底层的细节，这个方法跑出的结果和评分。

2.2 你刚提到了使用召回内容上下文扩充的技巧，那什么时候需要采取这种策略呢？

（可以看出面试问的很细，是会一个问题追着问的，这个问题在《大模型RAG实战》第4节讲得很清楚，我直接用书中原话作为回答）

在RAG场景下，通常将从向量数据库中召回的文本直接输入到LLM中。然而，由于向量化模型对长文本的编码有较大的信息损失，因此通常从向量数据库中召回的是短文本，但是对于LLM来说，连贯且包含更多上下文信息的长文本能够帮助总结出更好的答案。直接召回长文本可能比较困难，这时可以通过召回内容上下文补充的方法， 打破 "召回内容和输入LLM中内容相等"的约束，解决向量化模型需要短文本而LLM需要长文本的问题。

10. Agent之间的通信你是怎么解决的？

10.1 多Agent 之间的通信通常还是会有这个安全的concern， 比如某个Agent的某些状态不应该要给到下一个Agent，你怎么去解决Agent 之间数据传递的敏感性问题

显式控制传递字段

◦
不要直接传整个对象，传递必要字段。
◦
可以用 数据过滤器（Data Filter）或 Schema 限制传递内容。

分级 Memory

◦
不要让所有 Agent 共用一个 Memory。
◦
可以按角色分配 Memory，或者用 Scoped Memory（只给某个 Agent访问）。

敏感信息标记 + 自动剔除

◦
给敏感字段打标签（如 sensitive=True），在传递前自动过滤。

沙箱隔离

◦
如果某个 Agent 是外部服务，限制它只能访问特定数据。
