查看解释与参考资料

向量数据库不会天然为对话历史做摘要，也不会自动缩短传给模型的上下文。

在我们要使用这个长期记忆的时候，我们就可以通过向量数据库的语义搜索的功能，召回相关的感兴趣部分，输入给大模型。

内容查询优化： 当用户的提问过于模糊的时候，我们通常会使用一些查询优化方法，扩充上下文的信息，对查询内容做处理。 比如对于这个问题，我们做了处理以后，原来文本 "今天天气怎么样" 就会变成 "10月1号的天气怎么样"。

再使用结合元数据召回的方法，在每个召回文档中，元数据会有一些标签，比如日期，结合这两个技巧，就能够准确实现用户问题的召回了。

10. Langchain里拿到这个流式响应，怎么实现的，使用的一些什么协议？

（涉及的点很多： Langchain的runnable, Python的异步迭代器，以及传输协议SSE， Websocket, Http Chunked. 如果都弄得很明白需要花一些功夫，时间不够的同学可以先理解掌握本题，具体深入的细节可以先放一放)

更正：stream 通常通过同步迭代器用 for 消费；astream 通过异步迭代器用 async for 消费。将结果通过 SSE 或其他协议推送给客户端是后端另一层工作。

查看解释与参考资料

stream 与 astream 的迭代方式不能一概说成异步。

在 LangChain 中，所有核心组件（模型、链、Agent 等）都被统一封装成一个抽象类 Runnable，它定义了标准调用接口，包括 invoke()（一次性输出）和 stream() / astream()（流式输出）。流式输出的这两个方法通过 Python 的异步迭代器，让开发者可以用 for 或 async for 循环逐块消费生成的内容，实现“边生成边处理”的能力。

更底层实现分为两层：

  • 后端内部：LangChain 迭代器从底层模型获取 token 或片段，前提是模型本身支持流式生成（如 OpenAI 的 stream=True）。
  • 后端对外传输：将这些 chunk 推送给客户端，常用三种协议：
a.
SSE（Server-Sent Events）：基于 HTTP 长连接，单向推送，浏览器用 EventSource 接收；
b.
WebSocket：双向实时，适合需要交互（如停止生成）；
c.
HTTP Chunked：普通 HTTP 分块传输，前端用 ReadableStream 读取。

客户端在 Python 或后端服务中消费流式响应时，本质就是遵循迭代器语法，用 for chunk in runnable.stream(...) 或 async for chunk in runnable.astream(...) 来一点一点接收并处理数据。

这里就以客户端来回答。

在客户端，如果需要同时调用多个 Agent 的 API 来提高并发度，常见的并发方法包括：多线程、多进程、协程、消息队列、线程池等。

由于调用远端 API 属于 I/O 密集型操作，因此：

  • 多进程并不适合这种场景，因为它更适用于 CPU 密集型任务，而且进程切换的开销较大。
  • 如果系统结构简单、并发量不高，可以使用多线程来快速实现并发。
  • 如果追求更高的并发效率，推荐使用协程，因为协程更加轻量，资源占用更低，适合处理大量并发的 I/O 请求。

消息队列则更适合用于任务解耦、异步处理和高并发任务调度的场景。它通常用于构建更复杂、可扩展的系统架构。
