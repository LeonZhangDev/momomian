14 Agent场景题

这里更新一些Agent场景题，或者说是系统架构设计题目。这类题目通常来说是比较难的。

难点一：需要你对Agent系统的全流程有宏观的理解。你至少设计过Agent架构，做过Agent项目，或者至少看过一些Agent架构，你才能够现场设计出来。另外，你设计Agent架构，最好设计得比较完整，比较合理，且有深度。

难点二：通常来说，你设计出来了架构以后，不会说就结束了。面试官肯定是要围绕着你设计的系统进行探讨，问你为什么这么设计，你要说得出来你的设计原因，架构选型，也要经得起推敲和讨论。这就要求我们对整个设计的架构的各方面都要了解，那对我们综合能力就提出了一些要求。

所以很多同学反馈过，Agent的系统架构的设计题很难，不会回答。我倒是想要多总结一些架构设计题，不过以我的经历，真的考架构设计的不多。今天可算逮到了一个真题，我们以这个真题来讲解如何攻破架构设计题，如何复习。

先说场景题目的准备策略和理论基础，其实Agent场景设计题的理论基础是我们整个Agent的理论部分，项目经验。因为它本身就是一个综合的题目，还会问你各种细节，所以相关问题都是理论基础。这么说大家有没有一点绝望？

哈哈，情况确实是这么个情况，这就是一个综合能力的考察。不过稍微可以画一下重点，对于架构设计也多少有一些模板。大家看了本节后设计起来应该会更容易。理论重点画一下特别关键的部分：

Multi-Agent架构：选单Agent还是多Agent，为什么，常见的Agent架构有啥，这些是设计架构最核心的。

开源项目部分：Claudecode部分，Hermes Agent, Openclaw, PI-Agent. 这些笔记里讲的每一个Agent的架构，我们都有讲，你要是看了笔记，可以看出来它们其实也是类似的，有很多通用的地方。强烈建议从Pi-agent开始看，因为它最简单。

然后就是面试真题，和面试官去讨论架构设计的部分，它的整个讨论的逻辑，问题，都是我们掌握好Agent架构设计的好的素材。比如

小红书一面，夸克千问二面。这两个面经有讨论架构设计，不过其他的面试多少都有讨论。滴滴Agent开发专门考了Agent架构设计，里面有精讲，这些都是我们攻克这一问题的素材。


14.1 解题思路

  • 拿到题目先建立分析框架，而不是急着堆细节。面对任何一个 Agent 场景，都可以从以下几个维度切入、逐层展开。其实你可以看出来我们的开源项目讲解，每个项目都有一个全局架构图，它的核心模块都是类似的，关键地方组成也比较相同：比如Agentic loop(react)，长期记忆，触发层整体框架是类似的，我们可以复用框架，结合填充下面的细节就好了：
◦
触发层：谁来触发、是同步还是异步、要不要分级路由把简单情况挡在 LLM 之外。
◦
Agent 架构：核心推理骨架长什么样——通常是 Agentic loop（ReAct），有些场景也可以用更受控的 Workflow（编排式）；关键是根据「延迟/成本/可审计」的要求，在「自由推理」和「固定编排」之间做取舍。
◦
记忆模块：靠什么沉淀经验、形成闭环学习，让这一次的结果能改进下一次。
◦
业务场景逻辑：把模型输出翻译成可执行动作（如分档、阈值、处置策略），这部分高度依赖具体业务。
  • 答题时沿着这几个维度展开，就能既有骨架又有细节。下面的「关键设计要点」正是按这个框架，落到「信用卡欺诈检测」这个具体场景上的一次完整设计。

14.2 信用卡欺诈检测Agent设计

此题选自202606 滴滴Agent开发（社招）面试真题。 整个面试几乎都围绕整个架构设计题讨论。

题目描述：

- 你可以获取客户的所有历史交易行为、商户信息等数据（也可以自行创造非结构化数据）。

- 现在新来一笔流水（交易），需要用 Agent 判断这笔交易是否为欺诈。

  • 要求围绕这个场景，设计并讨论整个 Agent 系统。

设计答案：

针对这个题目，我是设计了如下的架构图。设计要点在后面。框架我们可以复用，框架下面的细节，就是来自于我们的经验了。

关键设计

  1. 触发层：事件驱动 + 分级路由，把重活挡在 LLM 之外
  • 触发源按风控场景定义：主源是「一笔交易到来」（同步、要秒级返回）；辅源是定时 Cron、外部 Webhook（黑名单/情报）、人工复查——辅源只用来离线刷新画像和模式库，不阻塞实时链路。
  • Gateway 只做管道不做智能：认证、把不同来源归一化成标准 schema、幂等去重（同一笔只判一次，防重放）。这一层不调用 LLM。
  • Router 分级路由是时效关键：白名单/低风险 → 秒级放行；黑名单/硬规则 → 秒级拦截；只有落入灰区/可疑的交易才进入昂贵的 Agent 层。绝大多数交易在此就解决，省成本、保延迟。

  1. Agent架构：React模式

为什么这里选 ReAct loop 而不是 Workflow？ 选型的核心判据是「流程是否确定」。业务逻辑高度确定、步骤固定可枚举时（如「先查A→再查B→最后打分」这种不会因中间结果而变的固定管线），用 **Workflow（编排式）更好——路径可预测、延迟成本可控、易审计。而步骤灵活、需要 Agent 根据中间结果动态决定下一步、尤其需要 Agent 自己判断「是否收敛」**时（如本场景要判断「现有证据是否足够定案，够了就退出、不够就再追查一维」），就必须用 Agentic loop（ReAct）——因为「查哪些维度、要不要基于中间证据再追一手、什么时候停」无法预先写死，得靠模型边看边决策。本场景两种特征都有，所以采用「固定骨架（Workflow 的可控）+ 有界 ReAct（loop 的灵活）」的混合式。

  • 不放开让主 Agent 自由 fork 子 Agent，而是「预定义骨架 + 编排层有界 ReAct」的混合式——因为实时风控要延迟/成本可预测、可审计，纯自由推理路径不可控、且会放大错误。
  • Worker 池预先定义好（地理/速度、行为偏移、商户风险、设备与关联网络四个维度，相互独立、可并行）。这次调不调、调哪几个、要不要基于中间结果追加一手，由 Orchestrator 的有界 ReAct 决定：Think 该查哪些维度 → Act 并行调起子 Agent → Observe 收集证据 → Think 证据够吗？ 不够且未超上限就循环回 Act 追加一手，够了或达上限（最多 R 轮 / N 个 Worker / 超时）就收敛退出。
  • 每个 Worker 内部也是一个小 ReAct（感知→调工具查数据→局部研判出风险档→自检打置信度分），但目标和工具集被限死在单一维度，不会乱跑。Worker 之间只回传摘要给主 Agent，不共享全部中间过程，控制上下文膨胀。
  • 一句话：「固定编制的侦查队 + 一个会随机应变但受纪律约束的队长」。

  1. Critic 模式：两级复核，一轻一重，判官≠打分者

  • 更正：将自报信心与证据完整性分开记录；融合权重和阈值需要用适用的已标注数据验证及校准，并保留人工处理和证据不足状态。

    查看解释与参考资料

    Worker 自报 confidence 未经校准，不能直接作为可靠概率或自动降权依据。

    第①级 · Worker 内部自检（轻）：每个 Worker 出结论前给自己打个置信度分。不是独立 Agent，只是 prompt 里一步，便宜快，用来给每条信号带上 confidence，方便融合层按置信度过滤/降权，治噪声。
  • 第②级 · 独立复核 Critic（重）：位置在评分融合之后、决策之前。它是独立 Agent、独立干净上下文，只拿到「综合判定 + 完整证据链」，做对抗式复核，专门找「这个判定站不站得住、有没有把正常交易误判成欺诈」，压低误报。
  • 为什么必须独立、且在融合之后：单个 Worker 只有一维信息，站位不够，要等证据链拼全才有得审；而「做者不评自己的分」，让打分者自评会系统性高估，所以 Critic 必须换一个干净上下文。重活集中做一次，避免每个 Worker 都挂重 Critic 拖垮延迟。
  • （可选）第③级 · 人工兜底：只对「高额 / 低置信 / Critic 与打分层有分歧」的少数 case 转人工。

  1. 业务逻辑：决策分档，把风险分翻译成可执行的动作

为什么要专门谈业务逻辑？ 这一层其实和大模型本身没什么关系——它不涉及 prompt、推理、记忆这些「AI 味」很重的东西，纯粹是业务规则。但恰恰是这一层最能体现答题者的思维严谨性和边角 case 覆盖度：能不能想到「灰区不该非黑即白，而要给一个加验证的缓冲带」、能不能意识到「阈值是业务对误报/漏报成本的权衡而非技术最优」、能不能覆盖「高额、低置信、Critic 分歧」这些需要人工兜底的边界情况——这些细节比堆砌 AI 概念更能拉开区分度。把架构真正落到具体业务上，而不是停在通用框架，是这类题的加分项。


  • 风控的输出不是一个分数，而是一个动作：Agent 层最终给出的是「综合风险分 + 置信度 + 证据链」，但业务侧真正要的是「这笔到底放不放」。决策分档就是这层翻译——按风险高低切成几档，每档绑定一个明确处置动作，而不是让下游各自解读分数。
  • 分档与动作（典型四档）：① 低风险 → 直接放行（无感通过）；② 中风险 → 加验证（触发 3-D Secure / 短信验证码 / 人脸等 step-up，把决策权交还用户，既拦欺诈又不误伤）；③ 高风险 → 直接拦截（拒绝交易 + 通知）；④ 高额 / 低置信 / Critic 与打分层分歧 → 转人工复审。核心思想是给灰区一个「加验证」的缓冲带，而不是非黑即白。
  • 分档线由业务而非模型定：阈值不是技术最优解，而是业务对「误报 vs 漏报」成本的权衡——高价值商户/大额交易调保守（宁可多加验证），低风险场景调宽松（保通过率、保体验）。所以阈值要可配置、可按场景/额度/商户分层设定，并随记忆模块回流的真实指标动态调整。
  • 为什么单独成层：把「分档规则」从 Agent 推理里剥出来，好处是决策可解释、可审计、可快速调参——运营改一个阈值就能收紧/放松，不用动模型；也让同一套风险分能服务不同业务线的不同风险偏好。

  1. 记忆模块：用真实结果做沉淀，形成闭环学习

长期记忆是让 Agent 从「一次性判断」进化到「越用越聪明」的关键。建议设计的时候一定要设计上。笔记里其实讲过很多可复用的知识：**长期记忆到底该存什么？各个开源架构（如 ClaudeCode、Pi-agent、Hermes 等）的长期记忆模块分别沉淀了哪些东西、用什么结构组织？**设计时完全可以把这些经验迁移过来——比如「哪些该进画像、哪些进模式库、哪些只是短期上下文」，就是参照成熟架构的记忆分层思路，落到欺诈检测场景后的一次具体化。有这层积累，记忆模块才不会设计得空洞，而是有据可依。

  • 它不服务当前这笔交易，服务的是未来每一笔。当场给出的判定只是「预测」，判得对不对要等真实结果才知道——放行的过几天被投诉盗刷（说明漏报），拦截的被投诉「本人却被拦」（说明误报），或人工复查给出权威裁决。这些真相几小时/几天后才回流，所以是异步、事后。
  • 沉淀机制（拿到真实标签后做三件事）：① 更新账户风险画像（这个账户真被盗刷过 → 以后多留心）；② 更新欺诈模式库（新手法记下来，下次能认出）；③ 调整评分阈值（漏报变多就调低拦截线，误报太多就调高）。
  • 闭环：这些沉淀绕回喂给 Orchestrator，让下一次判定更准——「上一笔的教训，喂给下一笔」。同时，真实标签回流也是计算 Recall / Precision（评估准确率、驱动迭代）的唯一数据源，没有它整个评估体系无从谈起。
