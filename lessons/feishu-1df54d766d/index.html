8.3 面试前突击

第二小节，我们介绍了简历应该如何编写，如何包装，这个时候我们已经形成了我们的第一版简历了。在正式面试之前，针对于简历的内容：特别是你包装美化的功能点，甚至是虚构，没做过的功能和项目，建议面试前一定要突击准备一下。 准备的原则是：

1. 对于你美化过的内容，首先要说服自己，自己想通你是如何做的？比如数据是怎么来的，实验方法是什么，对照基准是什么？比如我简历里包装了是企业级的项目，那么这么复杂的功能是几个人做的，你主要负责什么？建议对照简历的内容，逐条的去思考。 简历里的所有你写的文字，就是面试过程中最可能问的高频考点，如果你自己写的内容，自己都没看，没想通，面试官问了你讲不清楚，这是大忌。

2. 对于你压根就没做的项目，我的个人建议是：你写一份非常清楚的设计文档，笔记里的RAG项目，算法项目，每个项目都有技术设计文档（我们又叫dev_spec)。写这个文档是一个很费时间的过程，但是写明白了，你对于项目的掌握就会清晰很多。你可以把它当作一个超级详细的系统设计任务，完成这个系统任务设计再去面试。

更正：答不上来时，明确哪些已经做过、哪些只设计或尚待验证，再说明下一步如何确认；不能用假装忘记掩盖未做过的事实。

查看解释与参考资料

刻意把未做过包装为忘记细节会抹去设计与实际经验的边界。

3. 不要要求自己一下掌握所有细节。 既然你是包装的内容，面试遇到细节答不上来很正常，允许自己面试有细节答不上来。 我们在第一场面试的原则：尽量不要过于露馅，有的地方答不上来，让面试官觉得是你确实不记得了，而不是在撒谎，作为第一次面试，就已经很成功了！ 但是，对于每一次面试，都是一个检验我们是否想清楚我们的项目的机会，请你把对应的答不上来的细节好好消化，继续想得更加深入。这样你会一场比一场面的好。

这一小节，展示一下我在面试前的突击内容。注意：由于时间原因，我这些内容大概花了一个工作日的时间准备的，同时对于我们虚构的这个项目，我并没有时间想好技术文档再去面试，所以我就先大概想清楚了它的架构图。如果时间充足：建议你按照这个思路，在面试前多准备一下，多抠一下细节，并且完成虚构项目的设计文档再去面试！


8.3.1 ForgePilot 项目

8.3.1.1 ForgePilot架构设计

我把我们笔记里写的虚构的自动修复bug的企业级Agent项目，叫做：ForgePilot。

如上面所说，对于虚构的项目，建议你是先写好技术文档，想清楚细节，写好技术文档再准备简历。

不过我的时间紧张，所以这个过程就没做，刚好也展示一下在时间紧迫的情况下，如何用一个虚构的项目去面试吧。

我的思路是面试前最少做以下准备：

1.先想清楚该项目基本需求，架构图是什么，有哪些模块，如何运作的。这也是为什么我加了一个3.1小节架构设计。

2. 想清楚这个内容，再去根据简历内容，一条条预测面试可能问的问题，把细节弄透，这个是3.2小节讲的内容。


8.3.1.1.1 项目背景

💡说清楚痛点，为什么传统Coding Agent已经很成熟了，还要自己做企业定制Agent。

通用 Coding Agent 能够辅助改码，但企业研发还面临上下文分散、工程流程复杂和人工审核受限的问题：团队代码资产超过 300GB，跨仓库、跨分支定位难以仅靠当前本地工作区搜索；bug单 的问题描述、评论、附件和关联单需要整理成完整任务；公司特定的构建、测试与返修流程需要固化，避免 Agent 反复试错和工程师持续跟进。同时，AI 加快代码产出后，人工 Review 可能成为新的瓶颈，需要结合变更意图、关键 diff、影响范围和验证证据帮助人理解与验收。


ForgePilot 的意义不是重造通用编码工具，而是复用成熟 Agent 能力，补齐企业上下文、交付闭环和可解释评审，将分散操作组织为团队可共享、可跟踪的任务。模型侧计划逐步适配公司自研本地模型，减少敏感数据外发，并通过经过授权的内部数据微调改善特定任务效果，评估降低长期推理成本的空间；本地部署仍需权限治理和成本、效果评测。


评测价值依据：用户提供的真实任务数据集评测结果为，定制平台相比通用 Claude Code 流程，端到端交付成功率提升 32%。具体评测平台与版本、成功标准、样本规模、对比条件及相对提升/百分点口径待补充；该结果不直接代表当前 ForgePilot 设计已实现或完成同等验证。

任务理解与路由编排

💡这一层加了一个本地模型，主要通过本地模型分类处理 + Harness实现信息提取，找了个合理需求把我们后训练项目嵌入其中。

这一层位于 Cordis 插件化执行层上方，由本地模型与 Harness 协作，将用户需求整理成可执行任务。Harness 指我们编写的流程控制与运行管理代码。

  • 本地模型——理解与分类：理解 Bug 单，提取问题现象、触发条件、实际结果和预期结果，识别缺失信息，并给出任务分类建议。
  • Harness——校验与上下文组装：校验模型输出，必要时请求用户补充；结合项目配置、权限、会话历史和相关记忆，准备执行上下文。
  • Harness——插件适配与路由：根据任务类型和项目要求，选择 Agent 引擎、检索器及执行工具等适配器，通过 Cordis 完成服务装配，再将任务交给 Pi 执行。
  • Harness——运行管理：跟踪任务状态，落实预算、取消和审批规则，并接收执行结果。

本地模型负责理解需求，Harness 负责确定性规则和执行准备，Cordis 负责插件装配。 新 Bug 按固定流程进行预处理，查询和审批等请求不必经过本地模型；模型分类不能代替权限判断。


💡 插件化，引入DSH的技术。同时我们项目背景里写了，有可能处理300+GB的大型仓库，所以针对于不同的项目来选择你的索引，是一个我们可以强调的技术，也和整个插件化的思想比较搭。 同时底层默认使用Pi Agent也是一个比较主流的技术。

Cordis 插件化执行层

Cordis 负责插件注册、依赖注入、装配与生命周期管理。业务依赖统一接口，不直接绑定某个具体实现，因此可以按项目配置替换执行能力。

  • AgentLoop，默认 Pi：维护当前执行上下文，组织模型调用与工具调用的循环，汇报执行过程和结果。
  • 主模型适配：对接选定的主模型，由模型分析原因、提出下一步动作和生成修改建议。
  • 检索插件：提供代码搜索和上下文获取能力；普通项目可用本地检索，大仓库可接企业检索服务。
  • 工具执行插件：在允许范围内实际执行读取、修改和测试等操作，将结果返回 Pi。

主模型、Pi 和工具共同形成 ReAct 式循环：模型提出动作 → Pi 调用工具 → 工具返回结果 → Pi 带着结果再次请求模型。 主模型不直接操作工作区。

Cordis 本身不进行模型推理；可替换性来自统一接口和适配器。更换实现仍须满足能力与安全约束，不表示运行中可以无条件切换引擎。


💡 会话管理和记忆模块，是必须有的模块。暂时没有精妙设计，我就先借鉴常见开源框架的策略来设计就好。

会话管理

持续保存对话消息、工具记录和执行进度，并在用户重新进入时加载历史，支持连续交互与过程追踪。它是运行期间的支撑机制，不是任务结束后的单独步骤。

保存会话不等于自动恢复所有正在运行的进程；具体任务恢复机制后续再设计。


记忆写入与召回

从任务过程中及结果中筛选、校验有价值的项目知识或有效经验，再写入长期记忆。后续任务按权限和相关性召回，供上层整合上下文。

会话记录保存“发生了什么”，长期记忆保留“哪些知识值得以后复用”。 不将全部历史消息自动当作记忆，也不将模型未经验证的猜测直接作为事实。

构建、打包与发布

1. 构建与打包流程



整体流程：前端与后端代码 → Electron 桌面产品 → CI/CD 流水线构建与测试 → electron-builder 打包 → Windows EXE 安装包。


  • 前端界面（React + TypeScript）：实现对话、任务、评审等界面，以及用户交互。构建后生成界面文件。
  • 本地后端（Node.js + TypeScript）：处理任务编排、工具调用、仓库操作等业务逻辑，在用户电脑上运行。
  • Electron 桌面产品：提供桌面窗口和运行环境，将前端界面与本地后端集成为桌面应用。
  • CI/CD 流水线：使用 GitHub Actions，或公司内部 Git 平台的 CI/CD 能力，自动执行代码构建、测试及打包命令。
  • electron-builder：将构建后的界面、后端、Electron 运行环境及所需依赖组织为可安装的应用，生成 Windows EXE 安装包。
  • Windows 安装包：用户下载并安装 ForgePilot，获得本地运行的应用；后续新版也通过安装包提供。

2. 发布与下载

流水线生成安装包后，将其上传至 GitHub Releases、公司内部制品平台或对象存储，获得下载链接。CI/CD 负责执行上传流程，制品平台负责保存和提供安装包。


用户可以通过两种入口获取软件，两种方式可以指向同一个安装包：

  • 企业内部邮件通知：说明版本号、更新内容，并附上安装包下载链接。
  • 官网或内部下载页面：展示版本号、更新说明和下载按钮。

发布流程：安装包上传至制品平台 → 邮件通知或下载页面提供链接 → 用户下载 → 安装或升级。

3. 安装后的使用方式

同一个安装包包含前端界面、本地后端和 Electron 运行环境，可以提供两种使用入口：

  • 桌面入口：启动 ForgePilot，通过 Electron 桌面窗口使用。
  • 本地浏览器入口：启动本地 Node 服务后，用已有的 Edge、Chrome 等浏览器访问本地地址，例如 http://localhost:7890，加载同一套前端界面。

浏览器入口需要在产品中实现，并对依赖 Electron 的界面功能进行适配；不需要再下发单独的浏览器安装包。


这里的 安装包下载链接 用于获取软件，本地界面地址 用于安装并启动后的日常使用，两者用途不同。

4. 更新方式

可以提供两种更新方式：

  • 用户主动更新：通过邮件或下载页面通知新版本，用户主动下载新的 EXE 安装包，安装并替换旧版应用。仅发布新链接不会自动升级已安装的软件。
  • 应用内自动更新：接入 Electron 应用的更新能力，可使用与 electron-builder 配套的 electron-updater。流水线发布新版安装包及更新元数据后，应用在启动时或定期检查更新，自动下载新版，并在合适的时机提示用户重启安装，无需用户再到网站手动下载。

5. 版本管理

导读：既然我们说我们的项目是上线的，怎么进行版本管理，迭代的，大概的思路和意识要有，万一聊到相关问题，不至于完全答不上来。

采用 Git 分支分工 + 应用版本号 + Git Tag + 发布记录 管理版本，组织开发与发布流程，并建立代码提交与安装包之间的对应关系。


分支分工与合并流程

以已发布稳定版 1.0.0 为起点，本例中 dev 与 main 的代码一致：

  • feature 功能分支：开发者从 dev 拉出，例如 feature/日志采集，在这里开发和提交代码。功能完成后提交 PR，审核通过后合回 dev，未完成的改动留在各自的功能分支。
  • dev 开发集成分支：汇集已完成的功能，进行集成测试，检查多个功能是否互相影响。准备发布时，确定本次发布的代码范围。
  • release 发布分支：发布负责人从 dev 的确定提交拉出，例如 release/1.1.0。测试人员验证，开发者修复问题，不加入下一版新功能。验证通过后，在 release 的确认提交上打 Tag，由流水线构建安装包并发布。
  • main 正式发布主线：保留已正式发布的代码，不用于日常功能开发。发布后，release 通过 PR 合入 main；release 上的修复也同步回 dev，避免下一版丢失修复。

整体路线：dev → 拉出 feature 开发 → PR 合回 dev → 拉出 release 验证修复 → 打 Tag 构建发布 → PR 合入 main。

6. 灰度发布

正式项目中通常采用 灰度发布：安装包准备好后，不立即向全量用户推广，而是先让部分用户安装使用，观察运行情况和用户反馈。发现问题时，暂停扩大范围，及时修复或回滚；确认小范围使用没有明显问题后，再逐步向更多用户发布，最终完成全量发布。

灰度发布有多种实现方式。例如，通过在线更新服务和配置，自动控制哪些用户可以收到新版，以及每批下发的比例。这类方式适合用户规模较大、需要精细控制发布范围的场景。

我们的ForgePilot 定位于 企业内部使用，用户规模约为几百名开发者，因此采用更简单的 分批邮件通知 方式进行灰度，不引入复杂的在线比例控制机制：


  • 先通知部分用户：选择少量开发者或试用团队，发送包含版本说明、安装包下载链接和反馈方式的邮件，由用户下载安装新版。
  • 观察反馈并处理问题：收集使用反馈，检查核心功能和稳定性。出现问题时暂停后续通知，及时修复或按回滚流程恢复，验证通过后再继续推广。
  • 逐步扩大通知范围：小范围验证通过后，分批通知更多团队和开发者，持续观察反馈，最后向全体目标用户发送更新通知。

整体流程：安装包准备好 → 小范围邮件通知 → 观察反馈 → 逐步扩大范围 → 全量通知。

7. 回滚与版本恢复

新版发布后发现问题，先停止继续推广，避免影响更多用户。如果问题严重、需要尽快恢复使用，则让受影响的用户先回退到旧的稳定版本；待问题修复并验证通过后，再提供新版本。

  • 先停止发布：暂停后续邮件通知，撤下异常版本的下载推荐；如果已开放自动更新，也暂停该版本的更新推送，并通知已安装用户。
  • 紧急时回退旧版：提供上一稳定版本的安装包和操作说明，让受影响的用户按说明重新安装。回退前确认旧版与本地数据、配置兼容，必要时先备份；暂停发布本身不会让已安装的软件自动回退。
  • 修复后发布新版：开发者修复问题，测试通过后使用新的版本号重新打包，例如将有问题的 1.1.0 修复为 1.1.1。先通知小范围用户验证，确认正常后，再逐步向其他用户发布。

整体思路：停止发布 → 必要时回退旧的稳定版 → 修复并验证 → 发布新版。

8. 日志采集与分析

导读：这个做法是最典型的上线后分析问题的做法，埋点，上传，聚合，分析。 我们这里先清楚这种行业标准的做法，至于埋哪些点，聚合了什么数据，如何分析解决的，这些具体的细节，我们应该在该项目的技术文档写好。但是在面试突击章节，我们先掌握原理就好了，在面试问题预测里面，相关的面试问题，结合该理论，构造一个细节且具体的答案就可以了。

ForgePilot 在用户电脑上运行，通过 关键环节埋点 → 日志上报 → 远端集中存储 → Dashboard 分析，了解产品使用情况、定位问题，并辅助判断新版是否稳定。


  • 关键环节埋点：在任务开始、阶段执行、工具调用、任务结束及异常处理等关键位置记录结构化日志，便于关联一次任务的执行过程。
  • 日志上报：客户端将日志脱敏后，通过 HTTPS 批量上报到远端日志接收服务。网络异常时在本地限量缓存，恢复后重试，不影响正常任务执行。
  • 远端聚合：日志接收服务统一接收和校验各客户端上报的日志，集中存储到日志平台，供后续查询、统计和分析。
  • Dashboard 分析：围绕使用情况、任务成功率、执行耗时、异常趋势和不同版本表现建立看板。灰度期间观察新版是否出现异常增长；用户反馈问题时，按任务关联信息查询日志，定位失败阶段，再下钻查看具体记录。

整体流程：客户端埋点 → 批量上报 → 远端日志平台 → 看板观察与日志查询 → 定位问题并改进。日志查询仅向授权人员开放。

这个项目我没有设计专门的鉴权系统，也就是说整个产品对于所有人来说的都是可以用的，你可以直接下载客户端，任何人都能使用。

8.3.2.1 上线方案


本文描述团队内部使用的上线方案。远端 Streamable HTTP 与企业认证按以下方案实现并验证，不将方案描述为已经完成的上线成果。


整体运行原理

本系统以远端 MCP Server 的形式部署在团队共用的 VM 上。用户使用 Cursor、VS Code + GitHub Copilot 或 Claude Code 等支持远端 MCP OAuth 的客户端，配置服务地址并完成公司账号登录，即可调用知识查询工具

客户端与服务端通过 Streamable HTTP（基于 HTTPS） 交互。文档获取、解析、分块、向量化、索引维护和检索等工作全部在远端完成，客户端无需安装 RAG 模型，也无需处理文档或维护本地知识库。服务端返回检索证据和来源，客户端中的模型再根据这些内容组织答案。

MCP Server 内包含认证与权限模块，负责认证发现、企业登录衔接、Token 验证及文档访问控制。图中的认证模块与 RAG 模块是逻辑划分，不要求分别部署在不同服务器上。


整体流程：

配置远端 MCP 地址
 → 首次连接时发现认证要求
 → 使用公司账号登录并获取 Access Token
 → 通过 Streamable HTTP 携带 Token 调用服务
 → 服务端验证身份与文档权限
 → 检索并返回获授权的证据
 → 客户端整理为回答

1. 如何上线

1.1. 服务端部署

首版使用一台企业内网 VM，或通过企业网络访问的 Azure VM，集中运行 MCP Server、RAG 服务与后台文档处理任务。

上线时需要完成：

  1. 在 VM 上部署程序、依赖、模型和知识索引，并配置持久化存储。
  1. 将现有 MCP 接口提供为 Streamable HTTP 服务，配置 HTTPS 与稳定的服务地址。
  1. 完成认证与权限配置，不向未认证用户开放知识查询。
  1. 将程序作为后台服务运行，例如使用 systemd 或 Docker，支持开机自启与异常退出后重启。
  1. 自测连接、登录、查询、来源返回及无权限场景，确认正常后向团队开放。

2. 如何鉴权

2.1. 标准授权方案与企业身份系统

MCP OAuth 是 MCP 定义的、基于 OAuth 的标准授权方案，不绑定某一家企业的账号体系。 它约定客户端如何找到登录入口、获取 Access Token，并携带 Token 访问 MCP 服务。使用支持该方案的客户端，我们无需修改客户端代码。

Microsoft Entra ID 是本方案选择的企业身份系统，而不是 MCP 的必选项。 选择它是为了对接现有的微软企业账号与组织体系。其他公司也可以使用自己的统一身份系统，通过服务端认证模块完成适配，整体接入方式不变。更换身份系统后，需要验证与目标客户端的兼容性。

用户使用流程如下：

客户端连接 MCP Server
 → 服务端告知需要登录，并提供认证入口信息
 → 客户端引导用户使用公司账号登录
 → 登录成功后获取用于访问 MCP 服务的 Access Token
 → 客户端携带 Token，通过 Streamable HTTP 发起查询
 → 服务端验证身份和权限后返回结果

登录授权通过 HTTPS 完成，知识查询通过 Streamable HTTP（基于 HTTPS）完成。客户端负责管理登录凭证，不需要用户每次查询都手动登录。


2.2. 文档访问权限

身份系统确认“用户是谁”，服务端结合文档权限规则判断“用户能看什么”。 登录成功不代表可以访问全部知识库

例如，发布团队成员可以查询发布知识集合，组件 A 团队成员可以查询组件 A 的资料。服务端根据用户身份、所属团队与资料访问规则，只在用户有权访问的范围内检索，并对摘要等读取操作执行同样的检查。

凭证无效时提示重新登录；没有相应权限时拒绝访问，不透露无权文档的内容。后台服务能够读取资料，也不能将这些资料开放给所有用户。接入的资料还应符合企业对客户端模型使用内部数据的规定。

我们主要从两个维度判断任务是否修复成功：一是能不能自主完成，二是修复结果是否符合验收要求。

首先是自主完成。从代码定位、修改，到编译构建、运行测试，以及失败后的返修，都需要 Agent 在规定预算内自行完成。过程中不能由人工帮它改代码，也不能人工告诉它根因和具体修法，但允许它根据构建、测试的反馈自行调整和重试。任务结束后人工审核结果，不算帮助它完成修复。

其次是代码正确性。我们参考了 SWE-bench 的做法，为每条任务准备对应的单元测试、必要的端到端测试和相关回归测试。核心是验证两件事：原来能够复现 Bug 的测试，修复后要通过；原本正常的功能，修复后不能被破坏。 这里不是模型说自己修好了就算成功，而是必须实际运行测试，由评测程序检查执行结果。

除了功能测试，每条任务还会整理相关的架构约束和关键设计要求，比如不能破坏公共接口兼容性、不能绕过权限校验、不能违反模块依赖关系。能够自动检查的通过规则和测试验证，其余通过代码审核判断。即使测试通过了，只要明确违反这些硬性约束，我们也不认为修复成功。我们不要求它的代码和历史修复 PR 一模一样，但要求它修得对，而且符合项目的工程要求。

只有自主完成和结果验收这两个维度都通过，我们才把这条任务记为端到端修复成功。

8.3.4.1.2.2 已经有 Claude Code 等通用 Coding 平台，为什么你们公司还需要搭建自己的平台？

💡 答题思路：这个问题，我觉得是大部分面试官看到我们项目，第一个自然的反应。不过我在立项的时候，就想清楚了这个事情的答案，找了做这个事情的真实的痛点。


🗣️ 参考回答

我们不是要重新做一个 Claude Code，而是复用通用 Agent 的编码能力，补齐企业场景中的上下文、交付流程和安全要求。主要有六个原因。

第一，大规模代码检索。 团队代码资产超过 300GB，涉及多个仓库和分支，仅靠当前本地工作区搜索可能漏掉相关代码或找到错误版本，需要接入企业检索服务。

第二，企业任务理解。 TAPD 缺陷单的信息散在描述、评论、附件和关联单中，需要先整理成完整任务，避免 Agent 根据不完整的信息走错方向。

第三，减少流程试错。 公司有特定的构建、排障和测试方法，我们把确定的流程固化下来，不让 Agent 每次重新摸索，也减少工程师带路的时间。

第四，提高交付成功率。 写完代码不等于修复完成，我们关注构建、测试、失败反馈和返修的完整闭环。真实任务数据集上的评测结果显示，定制平台相比通用 Claude Code 流程，端到端交付成功率提升了 32%，这也是定制工程流程价值的一个依据。

第五，降低人工 Review 成本。 AI 写得快，人不一定审得过来。平台将变更意图、关键 diff、影响范围和验证证据组织起来，帮助 Reviewer 快速理解修改，聚焦风险判断。

第六，逐步适配公司自研本地模型。 这是规划方向：让适合的任务在公司受控环境内处理，减少敏感数据外发，再通过内部授权数据微调改善特定任务效果，并评估成本收益，而不是默认本地模型一定更便宜、更准确。

所以，单点需求可以用 MCP、Skills 解决；平台化的意义，是让这些能力在团队内统一复用，形成从任务到可审核交付的完整流程，而不是重复造编码工具


8.3.4.1.2.2.1 追问：你讲到的降低人工 Review 成本，这个是怎么理解，可以展开说说吗？

💡 答题思路：在你讲了某个功能，内容，没展开讲的时候，面试官很容易追问。这个降低Review成本，也是我在需求一开始的时候，就设计的一个功能。当我们想清楚了功能设计，这个题很好回答。这个也是一开始我说，即使时间有限，没时间设计具体文档，也先想清楚项目的痛点，功能，架构这些最基本的问题。


🗣️ 参考回答：

我理解的降低人工 Review 成本，主要是降低人理解代码变更的成本，而不是让 AI 替人批准代码。AI 加快了代码产出，但工程师仍然需要判断这些修改为什么做、是否合理、有没有验证。尤其当代码不是自己写的，一个 PR 又涉及多个文件时，理解修改思路本身就很耗时。

传统 PR 主要按文件展示红绿 diff，它能告诉你“哪些行变了”，但跨文件的修改关系往往需要 Reviewer 自己拼出来。我们希望参考 CodeRabbit Change Stack 按逻辑组织变更的方式，把分散在多个文件里的 diff，按修改意图重新分组，并关联说明和验证证据，而不只是额外生成一段 PR 摘要。

举个例子，Agent 要修复“请求失败后无限重试”的 Bug，可能同时修改配置文件、请求逻辑和测试文件。传统方式需要人来回翻这三个文件；我们希望先说明这次修复的目标，再按“定义并执行重试上限、传递重试次数、验证停止条件”组织阅读顺序。Reviewer 点开一个逻辑分组，就能看到相关的真实 diff，以及对应的测试和执行结果，再判断次数边界是否正确、测试是否覆盖原始问题。

这样降低的是寻找相关代码、跨文件切换和重建修改思路的成本，让人把精力更多放在行为是否正确、边界条件是否覆盖上。同时可以折叠格式调整、代码搬迁等噪声，但必须保留完整原始 diff 和未分组变更；说明要能跳转到代码和证据，未验证的地方明确标出，不能因为 AI 解释得顺就认为代码正确。

所以，这个功能的定位是面向 AI 研发交付的变更理解与验收辅助。目前属于设计方案，后续需要通过评审耗时和问题发现情况验证它是否真的降低成本，而不是只看页面是否更好看。

8.3.4.1.2.3 你在简历里提到了上下文压缩和运行态恢复，具体是怎么做的？

对应简历以下描述，预测的问题：

针对长任务上下文超限与摘要后状态丢失，按窗口预算压缩历史、保留近期交互，并保存与恢复关键运行态；通过工具输出分档裁剪、完整工具调用轮次回收及有界恢复与熔断，减少上下文溢出引发的重复失败。


💡 答题思路：

这道题的回答严格围绕简历要点展开，解释清楚简历写了啥。这个下面的策略，其实也是很多经典Harness框架，使用的一些常见方法了。

  1. 按窗口预算压缩历史、保留近期交互：用窗口占用比例解释触发条件——低于 80% 正常执行，达到 80% 先裁剪工具结果，仍达到阈值才摘要旧历史；按窗口容量约 16% 的 Token 额度保留近期交互，而不是固定保留几轮。
  1. 工具输出分档裁剪、完整工具调用轮次回收：说明短、中、超长结果分别如何处理，以及为什么调用消息和对应结果必须成组处理；用“之后只把摘要发给模型，完整消息保存在会话记录里”解释回收，避免抽象措辞。
  1. 保存与恢复关键运行态：讲清记录哪些任务信息，以及压缩后如何继续原来的工作；用“等待回归测试结果”的例子说明，避免只说保存状态、不说实际用途。
  1. 有界恢复与熔断、减少重复失败：明确溢出后先缩减输入，再重试原任务，最多一次；仍然超限就保存进度并停止自动执行。这里的熔断是任务级停止自动重试，不扩展为服务级熔断器。

🗣️ 参考回答：

我们主要处理长任务中的两类问题：一是代码、日志不断累积，超过模型的上下文容量；二是压缩历史时漏掉任务进度，导致 Agent 重复操作。参考 DSH 的做法，方案分成四部分。

第一，按 Token 预算压缩历史，保留近期交互。

每次请求模型前，检查上下文的 Token 占用。低于模型窗口的 80% 时正常执行；达到 80% 时，先裁剪长工具结果，裁剪后仍达到 80%，再把较早的历史压成摘要。 摘要时，从最新消息往前保留约占窗口容量 16% 的近期交互，其余较早历史生成摘要；保留边界会适当调整，避免拆开工具调用和对应结果。

第二，工具输出分档裁剪，按完整调用组回收历史。

短结果直接保留，较长结果保留关键片段，超大日志保存成文件，只给模型预览和文件引用。压缩旧历史时，工具调用和对应结果一起处理，不能拆开。之后发给模型的是这段历史的摘要，而不是完整消息；完整消息仍保存在会话记录里，需要细节时可以查回原文。

第三，压缩前保存任务进度，压缩后补回关键信息。

我们会单独记录任务要求、当前做到哪一步、改了哪个版本，以及哪些测试已经通过。例如，压缩前正在“等待回归测试结果”，压缩后就把这个进度明确告诉 Agent，让它接着查询测试，而不是重新分析 Bug。正在运行的构建或测试还会记录作业 ID，恢复时根据 ID 查询实际结果。

第四，溢出后尝试压缩再重试，连续失败就停止。

如果模型报上下文超限，我们先裁剪长工具结果，不够再把更早的历史压成摘要。输入缩短到预算内后，让模型继续执行原来的任务，最多重试一次；如果仍然超限，就保存任务进度并停止自动执行，避免反复发送同一份超长输入。

8.3.4.1.2.4 你在简历里提到“基于历史 Bug 与修复 PR 构建分层评估链路”，这是什么意思，具体怎么做的？

对应简历以下描述，预测的问题：

针对评审质量难以量化、误报漏报难以定位的问题，基于历史 Bug 与修复 PR 构建分层评估链路，以文件及代码区间匹配定位问题，再用独立 LLM Judge 补充语义判断；输出误报、漏报与根因命中分析，为评审策略迭代提供可回放依据。

💡 答题思路：

这道题出自对简历中“基于历史 Bug 与修复 PR 构建分层评估链路”这条表述的提问。简历里的每一条表述，都是面试官提问的热门内容。 我们要针对每一个描述，自己先想清楚：这是什么意思？具体是如何做到的？先要说服自己，才能向面试官讲清楚。 这里的“分层评估”“文件及代码区间匹配”“独立 LLM Judge”“误报、漏报与根因命中”“可回放”，都要能用具体做法解释，不能只记住这些技术名词。


🗣️ 参考回答：

这条讲的是对 Agent 修复 Bug 中间过程的评估，重点检查它有没有找到正确的问题位置和 root cause，而不是只看最后有没有修好。

因为最终测试不通过，可能是根因分析错了，也可能是分析正确但修改有问题。我们希望通过这套评估，把失败原因分清楚，再针对性调整。具体分四步。

第一，用历史 Bug 和修复 PR 准备评估样本。

把 Bug 描述、相关日志和修复前的代码交给 Agent，让它定位问题。我们根据历史修复 PR，结合代码和验证结果，整理问题位置与根因，作为参考答案。参考答案只供评估使用，不提前给 Agent 看。

第二，先检查位置，再判断原因，形成分层评估。

先用程序比对 Agent 报告的文件和代码区间，看它是否找到了相关位置。但位置对上不代表分析正确，所以再用独立的 LLM Judge，对照代码和参考答案，判断它说的是不是同一个问题、有没有解释清楚根因。有争议的结果再人工复核。

第三，分析误报、漏报和根因命中情况。

误报是提出的问题经核实并不成立；漏报是参考答案中已经确认的问题没有被发现；根因命中则是正确解释了 Bug 为什么发生。没有匹配上参考答案的发现，也会进一步核查，不能直接当作误报。

这样就能区分：没找到问题、找到了但解释错了，还是根因正确却没修好。 不同情况对应不同的改进方向。

第四，保存样本和结果，支持回放复测。

我们保存 Bug 输入、代码 commit、模型和提示词配置、工具调用记录，以及 Agent 输出和评估结论。调整检索或提示词后，再用同一批 Bug、同一个代码起点重新运行，对比结果。这里只改变要验证的策略，其他条件尽量保持一致。

所以，这套机制的作用是：不仅知道 Agent 修复失败了，还能分析失败发生在哪个环节，并通过同一批案例复测改进是否有效。

这道题来自简历中的“长任务执行可靠性”。简历里的每一个描述都可能被追问，要先想清楚它是什么意思、具体如何做到，再向面试官解释。这里不是保证模型一定修好 Bug，而是说明程序如何管理整个修复流程：任务按什么顺序执行，怎么避免重复，失败后怎么返修，意外中断后怎么接着执行。

回答分四部分，与简历逐项对应：

  1. 状态驱动的修复—构建—验证：记录当前步骤，由程序根据执行结果安排下一步，而不是 Agent 说完成就算完成。
  1. 动作去重、并发控制和重试预算：同一请求或通知不重复触发动作，同一任务的分支不被多个 Agent 同时修改，自动返修不能无限循环。
  1. 追加验证证据，按条件续跑原会话与原 PR：把对应版本的报错和日志补充给 Agent，在已有修改上返修；区分代码问题与环境问题，并检查原 PR 是否仍可更新。
  1. 状态对账及中断恢复：服务意外中断后，核对构建等外部任务的实际结果，结合保存的任务、会话和 PR 信息继续执行，避免重复启动和人工重新派发。本题不展开主动取消处理，简历原句中的“取消恢复”建议同步改为“中断恢复”。

🗣️ 参考回答：

这里的长任务执行可靠性，主要是指 Bug 修复要经过修改代码、构建、测试，可能还要多轮返修。我们通过程序管理这个过程，避免重复派发任务，或者构建一失败就丢下任务，需要人从头接手。具体分四部分。

第一，用任务状态控制修复、构建和验证的顺序。

系统记录任务正在修改代码、等待构建，还是执行测试，并根据结果安排下一步。代码修改完成才能构建，构建通过才能进入后续验证，测试没有完成就不能报告修复成功。这就是“状态驱动”。

第二，防止重复执行，并限制返修次数。

同一个请求重复送达，或者同一次构建失败通知来了两遍，只处理一次，这就是动作去重。同一个任务也不能同时启动两个 Agent 修改同一分支，这就是并发控制。自动返修还会设置次数限制，例如最多两轮，仍然失败就停止并转人工，而不是无限重试。

第三，失败后把报错补回原会话，在已有修改上继续返修。

构建或测试失败后，我们把对应的代码版本、执行命令、报错和日志补充给 Agent，让它根据这些证据继续修改，而不是重新分析整个任务。如果原 PR 仍然打开、分支和权限也允许继续，就把后续修改提交到原分支，更新原 PR。若只是构建环境故障，则先处理环境问题，不让 Agent 盲目改代码。

第四，意外中断后核对实际进度，从断点继续执行。

例如服务重启后，系统里还记录着“构建中”，我们会根据保存的构建 ID 查询实际结果：已经成功就继续验证，还在运行就等待，失败了就进入失败处理，而不是重新启动一次构建。这就是状态对账。结合之前保存的任务进度、会话和 PR 信息，系统可以从合适的步骤继续，不需要人工重新整理上下文、派发任务。

8.3.4.1.2.6 你在简历里提到“基础工具与代码智能增强方案的对照评估”，具体是什么意思？你是怎么评估 Agent 修复效果的？

对应简历以下描述，预测的问题：

针对代码智能工具对自动修复的实际增益难以判断的问题，基于 SWE-bench 完成基础工具与代码智能增强方案的对照评估，比较代码检索、调用图及结构上下文对修复任务的作用；以测试验证补丁有效性，结合单任务成本、工具调用次数与执行轨迹形成质量—成本对照分析，为工具增强与修复策略选型提供依据。

💡 答题思路：

这道题来自简历中的工具对照评估。先说明：我们建立了一套 Bug 修复评估集，通过增加或移除工具做对照实验，判断这些工具能否改善修复效果，以及增加的成本是否值得。 再按照“准备评估集 → 对照与消融 → 测试验收 → 分析并选型”展开，既解释简历，也讲清 Agent 的评估方法。

这里按之前确定的口径，使用的是借鉴 SWE-bench 方法构建的内部评估集，不是直接声称使用了官方数据集。简历原句中的“基于 SWE-bench”应在定稿时同步明确这一含义。本题细化第 2 题的修复评估方法，重点回答工具是否有收益；第 7 题则通过定位与根因分析，帮助解释修复失败的原因。

🗣️ 参考回答：

这条主要是说，我们不确定给 Agent 增加代码检索、函数调用关系查询等工具后，是否真的能帮助它修复 Bug，所以建立了一套评估集，通过对照和消融实验，比较修复效果与成本，再决定集成哪些工具。具体分四步。

第一，借鉴 SWE-bench 的方式准备评估集。

从历史 Bug 中整理问题描述、相关日志、修复前的代码版本、运行环境和验收测试。Agent 根据问题描述修改代码，历史修复答案不提供给它。数据分为调试集和独立测试集，前者用于调整工具方案，后者用于最终验证。

第二，固定其他条件，只改变工具组合。

让同一个 Agent 使用相同模型，在同一批任务、代码起点和预算下运行。基础方案只提供文件读取、文本搜索、编辑和执行命令等工具；然后分别加入代码检索、调用关系查询、代码结构查询等能力进行比较。也可以从完整方案中移除某个工具，观察效果变化，判断收益来自哪个工具，而不是只比较两套完全不同的系统。

第三，用测试判断补丁是否有效。

Agent 生成补丁后，在对应环境中执行构建、缺陷验证和相关回归测试。既检查原来的 Bug 是否修好，也检查是否破坏了已有功能。按统一标准统计任务解决率，而不是让模型自己判断“修复成功”。

第四，结合成本和执行过程决定工具选型。

除了看修好了多少任务，还记录单任务费用、耗时和工具调用次数，并查看执行轨迹。例如，调用关系查询是否帮助 Agent 更快找到相关代码，还是增加了大量查询却没有改善结果。

最后根据这些对比，决定哪些工具值得保留、哪些需要改进，或者只在特定任务中启用。调整的是 Agent 的工具组合，对比时使用的评估集保持一致。


8.3.4.1.2.7 本地模型处理问题

💡 答题思路：

因为我们简历里明确写了，我们这个Agent项目接入了本地模型。融入了我们后训练项目。简历里写的很多评估，训练方法，可以完全套用后训练项目的内容，就不展开了。唯一要想清楚的是和后训练不一样的地方：就是该项目中使用本地模型干什么？它的业务场景是啥，输入输出是啥？ 如果一开始的设计，我把本地模型的任务设置成了在解决bug之前，调用工具，搜集信息，产出结构化json字段。这个需求就完美和我们后训练项目适配了。


🗣️ 参考回答：

我们给本地模型的定位，是主 Agent 前面的一个任务理解与信息补全层。它不直接修 Bug，而是把 Ticket 和用户要求整理成结构化任务，判断还有哪些关键资料需要补齐，再由 Harness 组装上下文交给主 Agent。

它主要整理四类信息：第一是任务对象，也就是哪个工单、项目和仓库；第二是问题描述，包括实际现象、预期行为和已有复现线索；第三是执行条件，包括目标分支或版本，以及构建测试入口；第四是用户约束，比如只分析还是允许修改、不能改公共接口、不要新增依赖、暂时不要创建 PR。用户后续改口时，只更新被明确修改的字段，保留其他已有约束。

第二层是工具调用和任务分流。 我们为这一层设计了工单读取、评论和日志查询、项目与版本查询、代码检索及记忆召回等工具，模型通过多轮分析和工具调用补齐材料。当信息足以让主 Agent 开始工作，或者判断需要人工介入时，输出统一的结构化 JSON，包含 Bug 单信息、仓库与版本、问题现象、复现线索、用户约束、信息缺口，以及是否需要人工介入和介入原因。Harness 负责工具执行的权限与预算控制，并校验最终结果：满足条件就转到下层 AgentLoop，需要澄清就转人工；工具失败或达到循环上限则按规则回退，不无限等待信息完整。

第三层是训练和本地推理优化。 模型选用 Qwen3-0.6B。在已有结构化抽取实践中，SFT 主要解决“能否按要求正确输出”，包括固定 JSON 格式、字段归类、多轮状态继承和合法工具参数；DPO 则作为偏好优化的对照尝试，用于探索正确与错误候选之间的选择，例如信息不足时追问而不是猜测、保留已有约束而不是错误覆盖。实验中 DPO 没有体现出稳定增益，因此最终采用评测表现更合适的 SFT 方案，而不是默认叠加 DPO 就会更好。

推理侧使用 llama.cpp 本地部署，结合 GGUF 量化压缩和前缀缓存，分别减少模型资源占用和重复前缀计算，并通过回归评测检查质量变化。整体上，已有实验在解析质量和推理速度上都取得了改善，为 0.6B 小模型承担受控的任务解析工作提供了基础。迁移到 Ticket 场景后，再以字段正确性、约束保留、工具调用和人工分流的验收结果作为生产接入依据；不把原抽取实验直接等同于 Ticket 已经稳定上线。

帮助你更具体理解，列出模型大概要搜集什么信息，申请哪些工具供参考。

展开一：模型整理的四类信息

第一类是任务对象。 包括 Ticket 编号、项目、所属组件和目标仓库。优先通过工单与项目配置解析；如果存在多个候选且无法确定，就向用户澄清。

展开二：可以申请的工具

第一类是工单资料查询。 示例工具包括 ticket.get、ticket.list_comments 和 ticket.get_related，用于查询工单描述、补充评论和明确关联的工单。发现信息矛盾时记录冲突，不默认最新评论一定正确。

第二类是附件与日志读取。 示例工具包括 ticket.list_attachments 和 ticket.read_attachment_excerpt。先查看附件清单，再读取相关文本片段，并限制读取长度，不把全部附件塞入小模型。

第三类是项目与版本查询。 示例工具包括 project.get_config、project.lookup_component 和 repo.resolve_revision，用于查询组件到仓库的映射及工程配置，验证分支并解析代码版本。

第四类是有限代码检索。 示例工具包括 code.search 和 repo.read_excerpt，用于根据明确的错误码、符号或路径获取起步线索，以及读取工程说明。深度调用链分析仍留给主 Agent。

第五类是项目经验召回。 示例工具是 memory.search，用于召回有来源、经过验证且适用当前项目和版本的经验，并按权限过滤。

8.3.4.1.2.8 你如何对300+GB的代码仓库建立索引的？

💡 答题思路：面试官问这个问题是因为我们提到了，我们代码仓库很大，比如300+GB.使用的是GVFS仓库（也就是不会全量下载到本地的）。所以这个时候使用ClaudeCode本地处理肯定会失效。这是我们埋下的真实的痛点，面试官问这个问题很合理。


🗣️ 参考回答：

传统的 Agentic + grep 全仓搜索方案，在我们的 GVFS 大仓库场景下不适用。本地主要只有元数据，文件内容按需下载；grep 为了搜索而读取大量文件，会触发大量下载，延迟和资源开销不可控。如果只搜已下载的文件，又会漏掉大量代码。

所以我们设计了 “远端共享索引 + 本地增量覆盖 + 按需读取” 的方案，保留 Agent 多轮探索的能力，但不再依赖本地全仓扫描。

远端主要建立两类索引。第一类是代码全文索引，把文件路径、函数名、标识符和代码文本建立可检索的倒排索引，用来精确查找函数、错误码、配置项等，这是检索的基础。第二类是语义向量索引，按函数、类等结构切分代码，再生成向量，让用户用“登录失败后的重试逻辑在哪里”这样的自然语言，也能找到相关实现。

查询时，精确关键词走全文检索，功能描述结合向量检索，再合并、排序，返回代码片段和对应版本。我们优先复用已有企业搜索能力，通过检索插件接入，按需补充缺少的索引能力，不让每个开发者重复建一份全量索引

远端建索引当然也需要读取源码。我们不是消除了获取代码的成本，而是把全量获取和建索引集中到服务端，供有权限的开发者共享。后续按提交变化增量更新，而不是每次重新扫描整个仓库。

本地只补充分支差异和未提交修改，搜索时用本地版本覆盖远端旧版本，并屏蔽已删除文件。分析阶段优先从远端读取必要片段；真正需要编辑时，才通过 GVFS 下载目标文件，并核验当前版本，避免把主干代码误当成开发分支代码。

核心就是：服务端负责全局找代码，本地负责当前修改，GVFS 负责按需取文件。

8.3.4.1.3.1 项目长期记忆短期记忆要存一些什么内容？

💡思路： 虽然简历没特别强调，但是属于面试官老喜欢问的问题的了。结合我们讲的理论基础：Ageng记忆功能，先准备一下答案吧。


🗣️ 参考回答：

在 ForgePilot 里，我会把记忆分成短期和长期两层，短期记忆解决“当前任务怎么继续”，长期记忆解决“后续任务有哪些经验可以复用”。

短期记忆主要围绕当前研发任务保存：第一是用户的目标和约束，比如要修复什么 Bug、验收标准是什么、是否允许修改接口；第二是任务进度，比如已经完成复现、正在定位，还是等待测试和人工审核；第三是执行上下文，包括近期对话、工具调用结果、报错信息、当前代码版本和补丁引用，以及尚未验证的假设和待办事项。我们计划采用“结构化任务状态＋近期对话原文＋早期摘要”的方式管理，既支持任务中断后重建上下文，也控制 Token 消耗，而不是把所有聊天无限追加进去。

长期记忆则不存完整聊天，而是提炼四类值得跨任务复用的信息：项目的重要约束和决策背景、经过验证的修复案例、有证据的失败经验，以及用户明确表达的协作偏好。比如某个接口为什么必须兼容旧版本、某类并发问题之前如何修复和验证、某种方案在什么条件下失败，以及用户是否希望先确认方案再修改代码。

这些长期记忆要带上来源、适用项目、代码版本和验证状态。未经验证的模型猜测不会直接作为事实入库，密钥和一次性审批权限也不会作为可复用记忆。总体原则就是：短期存准确、可恢复的任务现场，长期存经过筛选、有证据、明确适用范围的经验。

8.3.4.1.3.2 你们这个系统是怎么发布的？

💡 答题思路： 按照上面的理论讲解

🗣️ 参考回答：

项目把 React 前端、Node.js 本地后端和 Electron 运行环境一起打包成桌面客户端。用户安装以后，任务编排、工具调用和仓库操作主要在他们自己的电脑上本地执行。

🗣️ 参考回答：

我们的版本管理方案主要用 Git 分支、应用版本号、Tag 和发布记录，解决两个问题：一是日常开发不要影响稳定版，二是每个安装包都能追溯到具体代码。


日常开发从 dev 拉出 feature 分支，功能完成后通过 PR 审核合回 dev。dev 用来集成已完成的功能，检查不同模块之间有没有冲突。准备发布时，从 dev 的确定提交拉出 release 分支，在这个分支上做发布验证和问题修复，不再加入下一版的新功能，让本次发布范围保持稳定。


验证通过后，在 release 的确认提交上打 Tag，例如 v1.1.0，由流水线针对这个 Tag 构建安装包，并记录版本号、代码提交和更新内容。这样用户反馈问题时，我们就能根据客户端版本找到对应安装包和代码，而不是拿最新开发代码去猜旧版的问题。发布后，release 合入 main，作为正式发布记录；发布期间的修复也同步回 dev，避免下一版把已经解决的问题重新带回来。


如果 1.1.0 发布后出现问题，我们暂停推广，必要时提供上一稳定版恢复使用，再发布 1.1.1 这样的修复版本，不直接覆盖原来的 Tag 或同版本安装包。这样既能并行开发，也能保证线上问题可追溯、可回退。

我们的排查思路主要是埋点、日志上传和看板观察。在任务执行、上下文压缩、工具调用等关键环节记录结构化日志，带上 session ID、任务 ID、客户端版本、执行阶段、耗时和异常信息，脱敏后批量上传到远端日志平台，再聚合成任务成功率、执行耗时、异常类型等指标，通过看板观察。所以不管是系统监控发现异常，还是用户反馈问题，我们都可以根据 session ID 找到对应会话，再按任务 ID 串起这次执行的完整链路，判断问题发生在哪个环节，而不是只根据用户描述去猜。


我就一个具体的例子，比如之前有个团队反馈系统：明明要求“修复 Bug，但不能修改公共接口”，Agent 最后却改了接口。针对这个问题，我排查的时候先找到对应 session 的执行记录，沿着工单解析、上下文组装和模型执行往下查。发现最初的模型输入包含这条要求，但任务中途触发压缩，压缩后的摘要没有保留它，后续输入也没有重新补充，于是我就能把问题定位到约束在压缩过程中丢失。再通过受控回放，对比压缩前后的输入和行为，验证这个判断。

修复时，把这类硬约束单独保存在结构化任务状态中，不只依赖聊天摘要，每次压缩后由 Harness 重新注入，并在提交前检查接口变更。最后回放这个失败任务，补充长日志、多轮压缩的回归用例，小范围发布后继续观察约束违规情况，确认修复没有引入新的问题。

8.3.4.2.3.1 请你讲一下你的RAG项目运行的逻辑？其他团队是如何接入的？

💡 答题思路：按照上面我们讲的要点：接入形式（客户端通过 mcp远端server streamable http通信），鉴权原理，后端运作方法（使用vm 部署长期rag服务）按逻辑串起来讲解。

🗣️ 参考回答：

这个项目的上线设计是把 RAG 做成团队共用的远端 MCP Server，各个团队成员使用本地Coding客户端接入。服务部署在企业内网或通过企业网络访问的 VM 上，长期运行，负责文档获取、解析、分块、向量化、索引维护和检索。客户端只负责调用工具，再由客户端里的模型根据返回的证据组织答案。


其他团队接入时，我们提供一份内部 Wiki，说明服务地址、网络要求、支持的客户端和配置方法。用户在 Cursor、VS Code 或 Claude Code 这类支持远端 MCP OAuth 的客户端里配置地址，通过基于 HTTPS 的 Streamable HTTP 连接服务，不需要安装我们的 RAG 程序，也不需要维护本地索引。


鉴权分成身份认证和资料授权两层。客户端按照 MCP 的 OAuth 授权流程引导用户使用公司账号登录，获取 Access Token，后续请求携带这个 Token。我们选择 Microsoft Entra ID 对接企业身份，服务端验证 Token 后，再根据用户所属团队和文档权限，限定可以检索的资料范围。登录成功不代表能查看全部知识库，摘要等读取操作也要执行相同的权限检查。


总结完整的链路是：配置地址、公司账号登录、携带 Token 调用工具、服务端在授权范围内检索、返回证据和来源，最后由客户端模型生成回答。后续只要接口和认证方式保持兼容，我们更新 VM 上的服务，用户通常不需要重新配置客户端。
