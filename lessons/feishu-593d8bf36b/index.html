先固定问题和验收方式

同一资料助手要回答退款条件和取消预约条件，共用6个教学样例、同一文档版本和判定规则。对比单 Agent、两个工作者加固定汇总、主管路由三个安排。数字是用于练习的给定记录，不是真实模型优劣或生产基准。

调用数不是角色数

一个工作者可能需要多轮，主管也会消耗路由和复核调用。比较时记录所有模型调用和跨角色消息，不只记工作者。并行能缩短部分关键路径，但总调用费、排队和汇总等待可能增加。

先解释失败来源，再决定要不要拆分

分工能减少单个角色的职责，但也会引入证据丢失、版本不一致和汇总冲突。若单 Agent 已完成同样任务，而协作只增加成本，应保留简单基线；若协作解决特定失败，也要用未参与调试的样例检验。

把输入代进去，走一遍

以下是本站固定教学样例，用来观察规则，不是线上服务的测量结果。

给定教学对比：单Agent=3调用、0条跨角色消息、1200 tokens、0.024元、6题对4题；双工作者+固定汇总=3调用、4消息、1800 tokens、0.036元、6题对5题；主管路由=5调用、6消息、2400 tokens、0.048元、6题对5题。

步骤当前内容或状态为什么这样变化
统一分母三种方案都以同样6题验收；成功率为4/6、5/6、5/6不能用每种架构各自最擅长的问题比较。
算质量差双工作者相对单Agent增加1题；提升1/6≈16.7个百分点这只描述本教学小样本，不是可推广的质量结论。
算资源差双工作者成本多0.012元；主管比双工作者再多0.012元主管这组数据没有新增正确题，却增加调用、消息和费用。
按目标选下一轮若允许0.04元，双工作者符合预算；主管超预算；仍需看失败题与新样例这不是自动宣布双工作者最好，选择还取决于实际任务、延迟和稳定性。

最后得到：能写出“在给定6题中多完成1题，额外花0.012元”，也能指出主管在本组没有新增质量收益。方案复杂度需要具体收益支撑。

如果这一步出错呢？

触发条件：把三个角色的结果随意合起来就说“比单 Agent 强”，却换了测试题或漏算主管成本。

单Agent测难题4/6，协作只测简单题5/5 → 分母与任务变了，差异无法归因架构。

恢复方法：固定同一输入集、版本和评分标准，记录全部调用、通信与失败，再用独立样例复测；并行延迟应实际计时，不能只用角色数推断。

（这个小节，我从参考论文的例子以及面试真题中抽取出来几个典型的例子和问题，帮助大家来掌握Agent架构设计相关的内容。现在很多面试都会考察一个小型的场景下的Agent架构设计题目，我会持续将架构设计相关内容汇总于此，这样大家复习更加方便。

在我整理了几个例子后，某种程度上，我觉得这个问题其实可以套模板，大家看一下是不是，如果你认为你的任务应该用去中心化架构，你就参考这个6.5.1,对于架构的好处，通信方式都可以复用，唯一不同的是Agent的设计和功能。）

8.5.1 动态网络浏览问题

（此例子截取自论文）

问题描述：我们需要通过网络搜索，找到 某公司2024年可持续发展报告中关于碳排放的问题，请你针对这个问题设计一个Agent架构。

架构设计：

因为网页导航是高熵，路径不唯一的场景。 不同的来源（官网，媒体，报告）可以被并行搜索更快覆盖。在这种场景下，我会使用去中心化架构设计整个系统，使用去中心化架构既能够提升并行速度，可以减少中心调度的串行瓶颈。

具体来讲，整个系统各个Agent是平级的，他们自主并行探索。系统里面使用事件总线/共享黑板的方式，所有Agent订阅相关话题，他们可以发布任务，认领任务，提供帮助，提交答案，来实现点对点的协作。

具体来讲，系统里有：

任务规划Agent，将用户目标拆分成子任务后，发布任务。

然后官网探索Agent， 媒体报告等Agent认领任务后，各自探索，调用工具汇总任务，直到达到标准然后会提交任务，交给验收Agent验收。

验收Agent验证通过后，交付给汇总机器人汇总信息，如果汇总Agent认为目标达成，及时发布停止信息，终止流程进行交付。


8.5.2 金融推理任务

（此例子截取自论文）

任务描述：设计一个分析某个上市公司的估值的Agent。

架构设计：金融估值的流程通常比较规范，天然具有分而治之的特点，多个子问题之间相对独立，可以并行。这种情况下我会使用中心化架构设计整个系统：由一个Orchestrator（中心指挥官）统一拆解，分派和收敛，降低并发协作带来的协调成本和不一致风险，确保各步骤按既定顺序和策略并发执行。

具体来讲：

我会先设计一个主管Agent, 他将任务分解成多个阶段，设计并行窗口，验收，将任务下发给子Agent去并行完成。

主管Agent下设置多个子Agent，比如收集官网信息Agent, 收集市场监管信息Agent，收集友商信息做对比的Agent。

整个过程由主管Agent负责验收，当Orchestrator验收通过，下发停止信号中止整个流程并交付。

8.5.4 时空冲突检测任务

（选自真题：夸克千问架构设计题目，我就准备直接套用6.5.2的模板）

任务描述：设计一个Agent系统，让它完成当用户创建一个行程后，判断这个行程是否和其它冲突，如果有冲突，给出重新规划的建议。

架构设计：行程冲突检测 和 规划本质是约束满足 + 顺序调整，流程比较规范，需要考虑时间窗口，地点，偏好等特点，这些因素也相对独立，可以并行。 这种情况下我会使用中心化 架构设计整个系统，由一个Orchestrator统一拆解，分派和收敛，降低并发协作带来的协调成本和不一致风险，确保各步骤按既定顺序执行也能够并发。

具体来讲：我会先设计一个Agent作为总指挥，根据当前阶段来分配下发任务，控制并发窗口，验收，和控制中止。

然后我会设计多个子Agent。 比如行程Agent：负责整理相关的行程，和行程时间相关的数据。 地点Agent：评估各个行程地点相关Agent的 通行时间等，冲突检测Agent, 用户喜好分析Agent 和 生成重新规划的Agent。 他们之间在某些阶段可以并行，某些阶段是串行，由主管Agent统筹规划和管理。
