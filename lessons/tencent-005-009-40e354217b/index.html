不要只数最后一句用户问题

模型可能同时接收系统要求、工具定义、历史消息、当前问题与检索证据。实际计数取决于模型的 tokenizer、消息包装和服务约定；汉字数、英文单词数、Python len 都不能直接替代真实 token 数。下面给定各部分计数，只练习预算分配。

输入之外，还要给答案留位置

假定教学窗口为 1000 token，计划最多输出 150，再留 50 余量，那么输入上限是 1000−150−50=800。余量用于吸收包装差异或后续变化，不是增加模型上下文窗口。若工具返回又增加内容，应在下一轮调用前重算。

压缩要考虑信息依赖

先保留任务约束、用户最新纠正和当前有效事实，再删旧闲聊或降低证据数量。工具调用与对应观察应按接口约定成组保留，避免只剩孤立的 tool 结果。超出预算时也可以询问更窄的问题或明确停止，不能静默删掉“不要提交”等约束。

步骤当前内容或状态为什么这样变化
1 · 算输入100+120+300+80+250=850把每个实际发送的部分计入，不能只算问题的 80。
2 · 算可用1000−150−50=800给输出和余量留位置后，输入最多使用 800。
3 · 算缺口850−800=50至少减少 50；一味调大 max_tokens 会让缺口更大。
4 · 改历史history 300→240；新输入 790在固定教学条件下删掉 60 的旧闲聊，同时保留最新约束与完整调用组。
5 · 重新核算790+150+50=990≤1000还剩 10 的计划余地；真实请求仍要用匹配的计数方式和实际服务用量核对。

最后得到：该教学方案可放入给定窗口。它说明怎样列账，不承诺真实提供商按这些数计费，也不证明被删信息对质量毫无影响。

原讲解与示例

了解 Token 与上下文窗口

在深入学习各类技巧之前，有一个底层概念不能跳过：Token（词元）。它直接决定了你能给 AI 多少信息，以及你要花多少钱。

什么是 Token？

更正：Token 是指定 tokenizer 的编码单位，可能对应字节片段、字符或多个字符；用匹配模型的 tokenizer 核算。

查看解释与参考资料

Token 与字符、单词没有固定大小关系，换算只能近似。

OpenAI token counting ↗

查看更正前的原段落

AI 模型不是以"字"或"词"为单位处理文本的，而是以 Token 为单位。Token 是介于字符和单词之间的文本片段：

  • 英文中，1 个单词 ≈ 1–2 个 Token
  • 中文中，1 个汉字 ≈ 1–2 个 Token（通常比英文消耗更多）
  • 标点符号、空格也各自占用 Token
  • 经验公式：1000 Token ≈ 750 个英文单词 ≈ 500 个中文汉字

上下文窗口：AI 的"工作记忆"

更正：按模型限制管理输入、输出及额外开销；超限行为须核对目标接口的拒绝、截断或压缩策略。

查看解释与参考资料

超窗并不必然自动遗忘最早内容，接口可能拒绝请求，应用也可能主动裁剪或摘要。

查看更正前的原段落

每个模型都有一个上下文窗口（Context Window），即它在一次对话中能处理的最大 Token 数量。超过这个上限，模型就会"忘记"最早的内容。


所有内容共享同一个上下文窗口，总量不能超过模型上限

Token 意识对提示词设计的影响

场景

Token 建议

System Prompt

精炼优先，去掉重复说明，核心规则控制在 500 Token 以内

输入长文档

先摘要再输入，或使用 RAG（检索增强）方式只传入相关片段

多轮对话

历史消息会累积消耗 Token，长对话要注意定期"重置"或压缩历史

API 开发

输入 Token + 输出 Token 都计费，输出通常比输入贵 2–3 倍

写作建议：把最重要的指令放在提示词的开头或结尾，中间位置的内容在长上下文中容易被模型"忽视"——这是大模型的已知特性，称为"迷失在中间（Lost in the Middle）"现象。
