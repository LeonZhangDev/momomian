7.5 Hermes Agent 架构解析

（对应第 10.4 节 OpenClaw 的 Agent 架构解析，回答"Hermes 的多 Agent 架构是什么"。因为Hermes Agent的架构和Openclaw非常像，虽然Agent架构是很重要的一部分，但这里没有什么新东西，就不赘述了）

7.5.1 概述：同样是递归 Centralized

Hermes 的 Agent 架构和 OpenClaw 一样是递归 Centralized：

  • Parent Agent（主 Agent）对最终回复负责
  • 通过 tool call 的方式 spawn subagent

  • 更正：默认采用一层子代理委派；需要递归编排时，应按对应版本提高 max_spawn_depth 并配置 orchestrator 角色。与 OpenClaw 比较时注明双方版本与设置。

    查看解释与参考资料

    当前 Hermes 官方说明默认 max_spawn_depth 为 1，默认子代理不能继续产生孙代理；递归需显式开启并满足角色与深度配置。

    Hermes 官方：子代理委派 ↗

    Subagent 可以继续 spawn 孙 Agent（默认深度比 OpenClaw 宽）

Hermes 的定位是 "agent loop first with this learning element"——loop 结构本身是常规的 Centralized，创新在于"learning element"。


7.5.2 Spawn 机制对比


更正：Hermes 可作为 ACP 服务端被调用，也有调用外部 ACP 进程的集成接口。组合 OpenClaw 与 Hermes 前应核对双方接口、启动参数、后端和工具权限。

查看解释与参考资料

ACP 指 Agent Client Protocol。Hermes 支持相关服务端及客户端集成，但角色双向不等于无需安装、后端或权限配置，也不是相对 OpenClaw 独有的差异。

Hermes 官方：ACP ↗

查看更正前的原段落

关键差异：Hermes 把 ACP 做成双向能力——不仅能调别人，还能被别人调。这让"OpenClaw 作 orchestrator、Hermes 作 worker"的组合变得开箱即用。


7.5.3 Agent 通信机制（和 OpenClaw 一样）

通信模式：Tool Call（而非 Handoff）——父 Agent 保留控制权。

更正：官方委派流程主要将子任务的最终摘要交回父上下文。子会话中的消息、工具轨迹和模型私有思考应区分；访问及日志边界需另行配置和验证。

查看解释与参考资料

最终摘要进入父上下文与“完整思维链保存在私有会话”是不同断言；隔离会话不证明模型私有推理会被完整保存或不可访问。

Hermes 官方：子代理委派 ↗

查看更正前的原段落

消息传递：仅最终结果，子 Agent 的 chain-of-thought 留在私有 session 里，父 Agent 只收到蒸馏后的回复。

更正：两者可以有相近的工具式委派结构；具体通信与生命周期差异应按版本和配置逐项核对。OpenClaw 当前也提供 ACP 外部运行时与 ACP 服务端桥接。

查看解释与参考资料

共同使用父子委派模式不能证明通信策略完全相同；异步交付、取消、权限和持久化等语义仍需逐项比较。

OpenClaw 官方：ACP Agents ↗

查看更正前的原段落

这和 OpenClaw 第 10.4.3 节的策略完全一致——两者在"多 Agent 通信"这块没有本质差异，都是业界主流做法。
