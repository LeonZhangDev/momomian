本课目标

  • 说明评测分数的样本、标准、算法和比较基线。
  • 用质量、时延和失败重试成本选择批次大小。
  • 说明共享预算的检查与扣减为何需要原子性。

本课机制与检查方向

先用这个入门例子理解流程，再看下方完整讲解。

本课问平均分81.7/100如何计算，首先应解释哪些信息？ 结论：评分标准、样本范围、计算方式与对照基线。 理由：一个分数只有结合定义和样本才能解释，也要说明是否参与调参及优化前结果。 配套示例：同一批100条样本按明确量表评分，再与旧版比较；不把自评平均分冒充线上成功率。 将5条内容合并给LLM评估后调用次数变少，能否直接断言5是最优批次？ 结论：不能，还需比较质量、上下文限制、延迟与失败成本。 理由：批处理减少部分请求开销，但更大上下文和整体重试也可能带来代价。 配套示例：固定样本比较1、5、20条的评估一致性、费用和P95，再选满足目标的批量。

知识点讲解

2026.08 阿里淘天秋招大模型开发

今天这一期内容，是26年8月秋招阿里淘天校招一面的内容。一面内容，基本上是围绕项目展开提问的。只有一个问题，MCP 相关的技术，只面试官主动提问的。

从这个角度来看，从八股，知识的角度上来分析，好像借鉴意义不大了。


不过换一个角度来思考：

因为本次面试大部分内容是围绕项目，简历来展开的。通过这个内容我们可以学习到面试官通常对简历是怎么提问题，喜欢怎么问，学会了这个，我们用这个方法论，可以在面试前提早预测面试重点，做好准备。

毫不夸张地说，学会了这个技巧，如果你做了好准备，面试前70的内容都是你准备过的题目，那么面试不就是十拿九稳了？


讲解知识之前，我们先说一下这个同学的背景：这个同学实习经历，本身的技术栈是和后端相关的，有比较丰富的后端实习经历，所以他的秋招一方面是投递： 后端 + AI的岗位，一方面是投递：纯AI(AI开发的岗位)。

本次面试的岗位，是纯AI的岗位。（我写这个是给后面分析面试官为什么会问一些后端的内容，来做一些铺垫）。


同时，对于问题的解析，有一些问题其实是可以复用到笔记里已有的项目的，所以对于这些问题的解析，我会按照我们笔记里的项目，来组织答案。

有一些问题是和这个同学个人背景（后端项目） 相关的，提问就围绕了后端内容 + 传统技术，那么这一块内容我会不解析答案，只是带大家分析面试官为什么会这么问。

我在这一期面经，把下面的每一条，如果是面试前可以预测出来的，我都标出来，大家看看在一次面试之前，有多少面试内容是可以提前准备好的？

一面

请简单做一下自我介绍。


你现在还在xx吗？

【可预测】同学的背景是留学生，所以面试官问这个也很合理。稍微提醒一点的是，回答要体现出稳定性，就是让面试官觉得你真的是要回国工作的，不要让面试官觉得你大概率比如想留在国外，那么他会认为你对这个offer的忠诚度不高，给了offer也可能不来，别踩这个坑。

为什么考虑回国工作？有没有考虑继续留在国外？

你老家是哪里的？


选一个你认为最能代表自己、比较经典的项目介绍一下。

【可预测】很典型的问题，我在我们ForgePilot项目面试前突击有说，如果你的项目是非常复杂的，企业级的合作的项目，那么首先想清楚的是你负责哪一块，包括简历里也要写出来。

在 xx 项目中，你的核心工作是生成商品描述，还是对生成的描述进行评估？


商品内容评估的指标是怎么确定的？怎么衡量生成内容的好坏？

【可预测】很典型的问题，我在我们ForgePilot面试前突击，简历编写的原则，这两个小节，我们都说了，对于任何一条出现在简历上的数据：都要想清楚：你对于这个数据是怎么测的？测试方法是什么？Baseline是什么？数据量有多大？应该如何进一步提升？

按照这个思路去分析，可以说，这个问题的主问题，4.1 4.2 4.3 三个小节，我们都是可以去预测出来的。 4.4 这个问题不是那么好预测，这需要我们一些灵活应变的能力，现场发挥。

简历里的平均分 81.7/100 是怎么计算出来的？

它的 baseline 是什么？有没有优化前的基准可以对比？

我将4.1 4.2这两个问题，套用到我们的ForgePilot项目，参考ForgePilot 项目面试真题预测：你提到在 180 条任务上，成功率从 31.11% 提升到 73.33%，相对提升约 135.71%，是怎么测出来的？什么算成功？

大家可以用这个方法，套用到自己的简历项目上，自己检验你是否把你的简历的内容想清楚了。


距离满分还差将近 20 分，具体不足在哪里？怎样向 100 分改进？

同样的，我还是把这个问题套用到了ForgePilot项目中，你也用这个问题检验自己的项目是否做好准备了没吧！


引入这套评估体系前后，整个产品链路最明显的变化是什么？

这个题不像上面三个题那么好面试前预测，需要一些灵活发挥的能力。这个题的解题思路和策略我还是套用到了ForgePilot项目中。


把五条数据合在一个批次里交给 LLM 评估，为什么能节省调用量？

【可预测】这个也是高度可以预测的。这个问题来自于面试官对于简历里写的内容的进一步询问。背景是同学简历里写了，他项目里的一个优化策略，是之前数据是一条一条输入给大模型，然后输出的，现在采用了优化策略就是，5条一起输入，统一返回一个结果。接下来面试官其实就是针对这个具体细节来问，这么做的好处是什么，为什么选择5条，有没有实验。

一直以来，我们都有一个经验就是，面试官特别喜欢问技术的选型，选什么LLM模型，选什么向量数据库，选什么Agent框架。这些我们都应该想清楚，同时这些所有问题的答案，最好是有科学的理论指导+实验对比，因为实验数据的结论是证明选型有效最有力的证据。 关于这一条的具体答案，我就不讲了，因为我们的项目没有相关问题，不具有参考性。

📝 参考回答

Claude Code 和 Codex 的基础代码检索都可以概括为 Agentic Search + grep/ripgrep：模型自己决定搜什么，读取命中的代码，再根据新线索继续搜索。Claude Code 主要通过专用搜索工具调用，Codex 的公开本地实现则通过命令执行工具运行 rg。这种方式灵活，能直接查看工作区的最新代码，很适合跨文件探索和问题排查。

我们采用 关键词 + 向量双路检索，并不是认为这种方式不好，而是做了不同的取舍：关键词检索匹配函数名、配置项等明确线索，向量检索补充自然语言描述与代码之间的 语义匹配，再把融合、筛选后的相关片段交给模型。

更正：多轮任务中，索引可能减少重复扫描和上下文输入；应在同一组任务上比较检索质量、延迟、Token 和维护成本。

查看解释与参考资料

索引是否节省时间和 Token 取决于任务、命中率及索引维护成本，不能作为必然结论。

我们看重的是在线延迟和 Token预算的可控性。通过预建索引，尽量在一次检索中找齐证据，减少模型反复“决定搜什么—调用工具—读取结果”的往返，也减少中间内容进入上下文。我们的代码相对来说比较稳定，修改不会特别频繁，更多的情况是基于代码仓库，进行理解和分析，这样在代码变动后，进行分块，向量维护的开销的成本会降低，在多轮对话中，检索速度更快，也会更省Token的好处会更明显。
