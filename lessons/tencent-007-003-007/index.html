父图和子图怎样交换字段

  • 把父图字段映射成子图输入，再映射回结果
  • 区分一次调用私有状态和跨调用保留的状态
  • 不把子图里的所有数据泄漏给父图
卡住时，先补哪一小节？
  • 先理解状态字段与合并

子图是有输入输出的一个流程

父图处理资料问题，子图只负责检索。父图字段叫 question，子图字段叫 query，这两个名字不会因为意思接近就自动相连。使用包装节点显式传入和读回，就像把外部表单转换成内部登记表。

返回需要的字段，保留私有细节

父图需要 evidence，不一定需要子图的临时改写词或内部消息。包装节点将 hits 映射为 evidence，限制输出范围。父子图共享状态键时可使用共享通道方式，但仍要读清 schema 与 reducer，不能凭相同名字假定所有语义一致。

第二次调用最容易暴露生命周期问题

本课约定 per-call 表示每次调用从新的检索临时状态开始；需要跨调用记住内容时才配置明确的持久化策略与会话归属。具体 per-invocation/per-thread 选项依安装版本核对，不能把普通 Python 全局变量当作可靠会话存储。

把输入代进去，走一遍

以下是本站固定教学样例，用来观察规则，不是线上服务的测量结果。

教学父状态={question:退款期限？,evidence:[],answer:空}；子状态约定={query,hits,scratch}；固定检索 hits=[refund-v2#3]，scratch=过滤旧版本。

步骤当前内容或状态为什么这样变化
父到子映射{question:退款期限？} → {query:退款期限？,hits:[]}包装节点明确改名 question→query，不把整个父状态无差别传入。
子图独立工作query保留；hits=[refund-v2#3]；scratch=过滤旧版本子图可以有父图不关心的临时字段。
子到父映射return {evidence:child.hits}父图只更新 evidence，scratch 不随之泄漏。
第二次调用新问题“取消预约？” → 新query；per-call hits=[]再检索不沿用第一次的临时 hits；若显式使用持久化，也须按契约决定读写哪些跨调用内容。

最后得到：父图得到证据，并继续生成回答；子图临时字段不需要暴露。生命周期通过第二次不同输入的调用检查，而非只看第一次成功。

查看完整 Python 推导与预期输出

标准库教学程序。固定输入的输出会随课程构建核对；不访问模型或外部服务。

def retrieve(child):
    return {"query": child["query"], "hits": ["refund-v2#3"], "scratch": "过滤旧版本"}

def wrapper(parent):
    child = retrieve({"query": parent["question"], "hits": []})
    return {"evidence": child["hits"]}

result = wrapper({"question": "退款期限？", "answer": ""})
print(result)
print("scratch" in result)

预期输出：

{'evidence': ['refund-v2#3']}
False

如果这一步出错呢？

触发条件：把 question 不改名直接传入只接收 query 的子图，或把上次 hits 全局复用。

第二次问取消预约 → 仍读第一次退款 hits → 回答引用退款期限，字段与任务发生错配。

恢复方法：用包装节点显式转换输入输出；每次调用初始化临时状态。要保留跨调用记忆时，采用明确会话键、持久化和权限边界，再测试不同用户与第二次输入。

子图

本指南解释了使用子图（subgraph）的机制。子图是一个图，在另一个图中用作节点。

子图适用于：

  • 构建多智能体系统
  • 在多个图中复用一组节点
  • 分布式开发：当希望不同团队独立处理图的不同部分时，可以将每个部分定义为一个子图。只要子图接口（输入和输出模式）得到遵守，父图就可以在不知道子图任何细节的情况下构建

添加子图时，需要定义父图和子图之间的通信方式：

  • 从节点调用图 —— 子图从父图的节点内部调用
  • 将图添加为节点 —— 子图直接作为节点添加到父图中，并与父图共享状态键（state keys）

从节点调用图

实现子图的一种简单方法是从另一个图的节点内部调用一个图。在这种情况下，子图可以拥有与父图完全不同的模式（没有共享的键）。例如，你可能希望在多智能体系统中为每个智能体保留私有的消息历史记录。

如果你的应用属于这种情况，你需要定义一个调用子图的节点函数。该函数需要在调用子图之前将输入（父）状态转换为子图状态，并在从节点返回状态更新之前将结果转换回父状态。

子图持久化

当你使用子图时，需要决定在多次调用之间如何处理其内部数据。考虑一个将任务委派给专家子代理的客户支持机器人：“账单专家”子代理应该记住客户之前的问题，还是每次被调用时都重新开始？.compile() 上的 checkpointer 参数控制子图的持久化：

对于大多数应用程序（包括子代理处理独立请求的多代理系统），“每次调用”是合适的选择。当子代理需要多轮对话记忆时（例如，一个在多次交互中建立上下文的科研助手），请使用“每个线程”。

父图必须使用检查点器进行编译，子图的持久化功能（中断、状态检查、每线程记忆）才能生效。请参阅持久化文档。

以下示例使用 LangChain 的 create_agent，这是构建代理的常用方法。create_agent 在底层生成一个 LangGraph 图，因此所有子图持久化概念都直接适用。如果你使用原生 LangGraph StateGraph 构建，同样的模式和配置选项也适用——详情请参阅图 API 文档。

有状态

有状态子图继承父图的检查点器，从而支持中断、持久化和状态检查。两种有状态模式的区别在于状态保留的时间长短。

每次调用（默认）

这是大多数应用程序（包括将子代理作为工具调用的多代理系统）的推荐模式。它支持中断、持久化和并行调用，同时保持每次调用的隔离性。

当每次对子图的调用都是独立的，且子代理不需要记住之前调用的任何内容时，请使用每次调用持久化。这是最常见的模式，特别是对于多代理系统，其中子代理处理一次性请求，如“查找此客户的订单”或“总结此文档”。省略 checkpointer 或将其设置为 None。每次调用都重新开始，但在单次调用内，子图继承父图的检查点器，并可以使用 interrupt() 来暂停和恢复。以下示例使用两个子代理（水果专家、蔬菜专家），它们被包装为外部代理的工具：

每个线程

当子代理需要记住之前的交互时，请使用每线程持久化。例如，一个在多次交流中建立上下文的科研助手，或一个跟踪已编辑文件编码助手。子代理的对话历史和数据在同一线程的多次调用中累积。每次调用都从上次结束的地方继续。使用 checkpointer=True 编译以启用此行为。

每线程子图不支持并行工具调用。当 LLM 可以访问作为工具的每线程子代理时，它可能会尝试并行多次调用该工具（例如，同时询问水果专家关于苹果和香蕉的问题）。这会导致检查点冲突，因为两个调用都会写入同一个命名空间。以下示例使用 LangChain 的 ToolCallLimitMiddleware 来防止这种情况。如果你使用纯 LangGraph StateGraph 构建，你需要自己防止并行工具调用——例如，通过配置你的模型禁用并行工具调用，或添加逻辑确保同一子图不会被并行多次调用。

无状态

当你想像普通函数调用一样运行子代理且无需检查点开销时，请使用此模式。子图无法暂停/恢复，也无法从持久化执行中受益。使用 checkpointer=False 编译。

没有检查点，子图就没有持久化执行。如果进程在运行中崩溃，子图无法恢复，必须从开头重新运行。

检查点器参考

使用 .compile() 上的 checkpointer 参数控制子图持久化：
  • 中断 (HITL)：子图可以使用 interrupt() 暂停执行并等待用户输入，然后从中断处恢复。
  • 多轮记忆：子图在同一线程内的多次调用中保留其状态。每次调用都从上次结束的地方继续，而不是重新开始。
  • 多次调用（不同子图）：单个节点内可以调用多个不同的子图实例，而不会发生检查点命名空间冲突。
  • 多次调用（相同子图）：单个节点内可以多次调用相同的子图实例。对于状态持久化，这些调用会写入同一个检查点命名空间并发生冲突——请改用每次调用持久化。
  • 状态检查：子图的状态可通过 get_state(config, subgraphs=True) 获取，用于调试和监控。

查看子图状态

当你启用持久化时，可以使用 subgraphs 选项检查子图状态。对于无状态检查点（checkpointer=False），不会保存子图检查点，因此子图状态不可用。

查看子图状态要求 LangGraph 能够静态发现子图——即，它是作为节点添加或在节点内部调用。当子图在工具函数或其他间接方式（例如 subagents 模式）中调用时，此功能不起作用。无论嵌套如何，中断仍会传播到顶层图。
