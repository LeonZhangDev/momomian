先看依赖，再看并发上限

三个任务彼此不依赖，才可以考虑并行。即使都能并行，工具限流、连接池和共享资源仍会限制同时运行数量。下面的毫秒数是人为给定的服务时间，只用于排程计算，不是电脑实际计时结果。

Send 分发，Reducer 收集

图可以把不同输入分给同一个工作节点，再用合并规则收集子任务结果。每个结果带 task_id，才能识别缺失、重复和失败。若最后只写死一个“最佳答案”，就没有真正使用子任务输出，输入改变后也不会正确变化。

汇总要检查是否收齐

Map 负责独立计算，Reduce 负责按规则汇总。例如对 2、3、4 求平方后相加，结果是 4+9+16=29。若任务 C 超时，只有 4+9=13，不能仍宣布完整结果 29；应按任务约定返回部分结果或失败，并标记缺项。

以下是本站固定教学样例，用来观察规则，不是线上服务的测量结果。

教学任务 A=(2,100ms)、B=(3,200ms)、C=(4,300ms)，输出平方；无依赖，并发上限2；调度顺序 A、B、C；忽略调度开销。

步骤当前内容或状态为什么这样变化
串行基线A:0–100；B:100–300；C:300–600；总时长600ms依次执行三个独立任务，服务时间直接相加。
并行开始t=0 启动 A、B；C 等待；在途任务数=2不能因为有三个任务就突破并发上限。
空位继续分发t=100 A 返回4，启动 C；B在200返回9，C在400返回16C 使用 A 释放的空位；本题结束时间为400ms。
核对并汇总A=4、B=9、C=16 → 3个任务齐全 → sum=29结果按 task_id 核对，再做求和，不能依赖返回顺序或写死最终值。

最后得到：在给定假设下，串行600ms、并发上限2时400ms，理论节省200ms；总计算工作量未减少，实际系统还会有开销与抖动。

查看完整 Python 推导与预期输出

标准库教学程序。固定输入的输出会随课程构建核对；不访问模型或外部服务。

tasks = [("A", 2, 100), ("B", 3, 200), ("C", 4, 300)]
slots = [0, 0]
ends = []
results = {}
for name, value, duration in tasks:
    slot = min(range(len(slots)), key=lambda i: slots[i])
    start = slots[slot]
    slots[slot] = start + duration
    ends.append((name, start, slots[slot]))
    results[name] = value ** 2
print(ends)
print(max(slots), sum(results.values()))

预期输出：

[('A', 0, 100), ('B', 0, 200), ('C', 100, 400)]
400 29

如果这一步出错呢？

触发条件：C 超时，汇总节点却把缺项当零或输出预先写死的29。

收到 A=4、B=9；C=timeout → completed={A,B}，expected={A,B,C}，不满足完整交付。

恢复方法：保留成功项和 C 的失败信息；在剩余预算内仅重试允许重试的 C，或按约定返回“部分结果13，缺C”。取消后核对已启动任务，不假定它们都被撤销。

异步

在并发运行 IO 密集型 代码时（例如，向聊天模型提供商并发发出 API 请求），使用异步编程范式可以显著提高性能。

要将图的sync实现转换为async实现，您需要：

  1. 将nodes更新为使用async def而不是def。
  1. 适当更新内部代码以使用await。
  1. 根据需要调用图的.ainvoke或.astream。

因为许多 LangChain 对象实现了 Runnable 协议，该协议具有所有 sync 方法的 async 变体，所以将 sync 图升级为 async 图通常相当快。

请参见下面的示例。为了演示底层 LLM 的异步调用，我们将包含一个聊天模型：
