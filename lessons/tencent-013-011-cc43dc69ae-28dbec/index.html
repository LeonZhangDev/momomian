先给用户看将要执行的具体动作

审批应显示日期、人数和目标对象，不能只问一句“同意 AI 操作吗”。本课固定虚构预约草稿并计算版本。用户批准的是这份草稿；若日期或人数改变，应重新展示，不把旧批准套到新的动作上。

恢复不是跳过函数前半段

LangGraph 的动态 interrupt 恢复会重新进入对应节点，interrupt 之前的代码可能再次执行。把格式化草稿、读取状态等无副作用步骤放前面；真正创建放在明确批准之后，并使用稳定业务请求键。不要把“进入节点第二次”直接当成新的业务请求。

拒绝、批准和重复请求各有出口

拒绝应进入保留草稿或结束分支，不落到创建语句。批准后若回执丢失，应按原业务键查结果；同一批准被重复提交时，先核对待处理状态、草稿版本和既有回执。示例中的写入次数属于教学推导，不是未运行真实服务的结果。

把输入代进去，走一遍

以下是本站固定教学样例，用来观察规则，不是线上服务的测量结果。

教学草稿 v1={date:2030-06-12,people:2}；thread=t8；业务键 r1；初始预约数 0；用户可选择 reject、approve 或修改草稿。

步骤当前内容或状态为什么这样变化
生成草稿后暂停status=awaiting；draft=v1；预约数=0先展示动作再 interrupt，尚不执行创建。
拒绝路径resume=reject → status=rejected；预约数=0拒绝分支明确返回或结束，不向创建节点继续。
批准路径resume=approve(v1) → 核验版本 → create(r1,v1) → booking=B1这一条是与拒绝路径分别演练的分支，不是在拒绝后自动再批准。
回执丢失后核对查询 r1 → 已有 B1；内部补记 receipt=B1；预约数仍为1服务端幂等和查询共同防止把重复恢复变成新预约。

最后得到：拒绝分支写入 0 次；批准分支仅允许对应草稿的动作。相同业务键重复处理时复用既有回执，不能靠图检查点本身承诺全局恰好一次。

如果这一步出错呢？

触发条件：把 create 放在 interrupt 之前，或拒绝后没有退出节点。

create(r1) → interrupt → 恢复时节点前部重跑；若创建无幂等保护，可能重复写入。另一错误是 reject 后仍执行末尾 create。

恢复方法：让副作用在具体批准后执行，拒绝分支显式结束；生成稳定请求键，查询和复用已执行回执。草稿改变即换版本并重新核对批准，不复用旧内容的同意。

换个条件，自己判断

用户把人数从 2 改为 3，但仍提交旧草稿 v1 的批准。应如何处理？

先口述、画两行状态或改一个值即可。检查方法在提交小测后也可以回来核对。

  • 展示 v2 草稿并请求对应确认
  • 保留旧决定和新草稿版本，避免覆盖历史

更正：审批节点写入 approved 布尔字段；删除此普通边，使用条件边在 approved=True 时进 execute、False 时到 END。

查看解释与参考资料

批准和拒绝都返回状态更新，该普通边会在两种情况下继续执行。

import os
from dotenv import load_dotenv
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.types import Command, interrupt
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import HumanMessage

load_dotenv()

def request_node(state: MessagesState) -> dict:
 """接收用户请求"""
 return {"messages": state["messages"]}

def approval_node(state: MessagesState) -> dict:
 """审批节点：暂停等待人工审批"""
    last_msg = state["messages"][-1].content

 # 暂停执行，等待人工决策
    human_decision = interrupt({
 "question": "是否批准执行以下操作？",
 "action": last_msg
 })

 if human_decision == "approve":
 return {"messages": [{"role": "assistant", "content": f"操作已批准：{last_msg}"}]}
 else:
 return {"messages": [{"role": "assistant", "content": "操作已被拒绝。"}]}

def execute_node(state: MessagesState) -> dict:
 """执行节点"""
 return {"messages": [{"role": "assistant", "content": "任务执行完成！"}]}

# 构建图
builder = StateGraph(MessagesState)
builder.add_node("request", request_node)
builder.add_node("approval", approval_node)
builder.add_node("execute", execute_node)

builder.add_edge(START, "request")
builder.add_edge("request", "approval")
builder.add_edge("approval", "execute")
builder.add_edge("execute", END)

# 使用 checkpointer 编译图
checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# 每次对话使用唯一 thread_id
config = {"configurable": {"thread_id": "approval-session-001"}}

# Step 1: 启动图，会在 interrupt 处暂停
print("=== Step 1: 提交请求 ===")
result = graph.invoke(
 {"messages": [HumanMessage(content="请删除数据库中的所有测试数据")]},
    config=config
)
print("图已暂停，等待审批...")

# Step 2: 人工审批后，用 Command 恢复执行
print("\n=== Step 2: 人工审批 ===")
# 批准操作
result = graph.invoke(
    Command(resume="approve"),
    config=config
)
print(f"最终结果: {result['messages'][-1].content}")

# 如果要拒绝，使用：
# graph.invoke(Command(resume="reject"), config=config)

在边上设置断点

更正：若沿用前文 builder，断点改用已注册的 execute；若为独立示意，先定义并注册 sensitive_node。

查看解释与参考资料

前文 builder 只注册 request、approval、execute，未注册 sensitive_node。

# 另一种方式：在编译时指定断点
graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["sensitive_node"],   # 执行该节点前暂停
    # interrupt_after=["review_node"],     # 执行该节点后暂停
)

重要：checkpointer是实现interrupt功能的前提条件。没有 checkpointer，图无法保存暂停时的状态，也就无法在恢复时继续执行。MemorySaver 适合开发测试，生产环境建议使用 SqliteSaver 或其他持久化存储。
