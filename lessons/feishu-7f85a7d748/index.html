7.3 Hermes 记忆系统 · 静态结构

（高频考点：Agent记忆系统是Agent核心。大家看任何Agent的时候，都应该有意识，去了解一下它的记忆功能是如何实现的。其中记忆功能，大家可以思考两点：由哪几部分组成（静态），如何更新，压缩（动态），笔记的ClaudeCode架构也是这么组织的。想清楚这两点，就想清楚了一个Agent的记忆模块最核心的东西。）


7.3.1 总览：一个上下文窗口 + 三类数据源（+ 一个索引）

更正：先按实际版本列出内置记忆、项目上下文、会话历史、Skill 和外部提供商；“三源加索引”只保留为本课的概念分析图。

查看解释与参考资料

三类来源和一个索引可用作作者的教学模型，不能代替已核查的产品布局。当前 Hermes 官方区分 memories 下两份内置文件、SQLite 会话历史、Skill 与可选外部提供商。

Hermes Persistent Memory ↗

查看更正前的原段落

先给大家一个整体骨架：Hermes 的记忆系统由一个上下文窗口（Context Window）+ 三类数据源 + 一个索引组成。每轮推理，系统把三类数据源的内容拼进工作集、送给模型；索引只在数据源 1 里按需搜片段，不直接进工作集。下面先看这五个角色分别是什么。


三类数据源（真正进 Context 的内容都出自这三类）：

  1. 工作空间 md 文件——人写的（或自进化循环写的）配置和知识文件，包含 Bootstrap Files、memory/ 笔记、Skill Library
  1. Session Transcript——系统自动追加的完整对话日志 .jsonl
  1. Honcho User Model——外部独立服务，存用户画像

一个索引：

  • 更正：默认持久记忆由 memories/MEMORY.md 和 USER.md 提供启动快照，历史对话用 session_search 查询。若另配向量记忆提供商，应注明插件、来源与工具名。

    查看解释与参考资料

    Hermes 当前官方内置记忆工具是 memory，历史查询是 session_search/FTS5；本段 memory_search、memory_get 与 memory/ 文件向量索引未经 Hermes 官方实现支持，不能套用 OpenClaw。

    Hermes Persistent Memory：Session Search ↗

    Retrieval Index——为 memory/ 下的 md 文件建的向量+全文索引。它自己不进 Context——它的作用是让 memory_search 能快速从 md 文件里找到相关片段，真正进 Context 的是搜到的那段 md 原文。

7.3.2 Context Window · 上下文窗口

定位：固定大小的 token 容器（模型决定：Claude 200K、GPT-4 128K、Gemini 1M），不是一层记忆，是记忆的消费端。每轮推理前系统从四类数据源拼装内容填进来。

每轮被拼进来的内容（按源码 prompt_builder.py + context_engine.py 的顺序）：

  1. System Prompt（来自工作空间 md 文件）：SOUL.md + AGENTS.md + MEMORY.md + TOOLS.md + …
  1. Skill 系统提示（来自 Skill Library）：精简 skill 描述列表
  1. Honcho 摘要（来自 Honcho User Model）：用户画像的一段文字摘要
  1. 对话历史切片（来自 Session Transcript）：从 .jsonl 尾部加载的最近消息 + 已有压缩摘要

  1. 更正：是否预取、使用何种工具以及注入多少内容，取决于内置和外部记忆配置；不要把 memory_search 预检索画成所有 Hermes 运行的固定步骤。

    查看解释与参考资料

    这里声称 Context Engine 必定预先做 memory_search，却没有给出对应 Hermes 配置或源码。外部记忆提供商的自动注入行为也不应归于统一默认。

    Hermes Honcho Memory：recallMode ↗

    预检索片段（来自 memory/ 下的 md 文件，通过 Retrieval Index 搜到，Hermes 特色）：Context Engine 根据当前消息主动做一次 memory_search，把命中的 md 原文片段塞进来
  1. 当前用户消息 + 工具结果

关键性质：

  • 最大 token 消耗者通常是工具结果（文件读取、网页快照、API 响应）
  • Bootstrap Files 每轮都占空间，所以要尽量精简（SOUL.md 最容易写太长）
  • 满了就触发 Compaction（见 11.4.3）——压缩的是"当前上下文里的旧消息"，不是整个 .jsonl
  • 用 /status 监控使用量，建议 75–80% 时手动 /compress

7.3.3 工作空间 md 文件

这一类是磁盘上的 Markdown 文件，用户可以直接编辑，也会被 Agent / 自进化循环写入。虽然都叫"md 文件"，但按用途分成三块。

7.3.3.1 Bootstrap Files

定位：会话每次开始都从磁盘读、注入 system prompt 的"身份文件"。

更正：区分项目上下文发现、HERMES_HOME/SOUL.md 和 memories 下的内置记忆；原文件清单与目录只作待核实的历史材料。

查看解释与参考资料

当前官方上下文发现不是统一扫描 ~/.hermes/workspace 下的 OpenClaw 式八文件集合：项目说明从工作目录发现，SOUL.md 位于 HERMES_HOME，内置记忆另在 memories。

Hermes Context Files ↗

查看更正前的原段落

文件清单（位置：~/.hermes/workspace/，仓库根目录也有一份）：

  • AGENTS.md — 操作指令、行为规则（Hermes 主入口文件）
  • SOUL.md — 人格、语气、边界
  • USER.md — 用户身份信息（静态版，和 Honcho 互补）
  • TOOLS.md — 工具使用说明
  • IDENTITY.md — Agent 名称与风格

  • 更正：内置持久记忆位于所用 profile 的 memories 目录，MEMORY.md 与 USER.md 在会话启动时形成冻结快照；共享与子任务权限应另外核对。

    查看解释与参考资料

    Hermes 内置 MEMORY.md 的官方路径、预算与快照行为不同于本段主会话专用工作区文件说法。

    Hermes Persistent Memory：Frozen snapshot ↗

    MEMORY.md — 策展的长期记忆（仅主会话加载）
  • HEARTBEAT.md — 心跳任务清单（可选）
  • BOOTSTRAP.md — 首次运行仪式（一次性）

关键要点：

  • 更正：持久文件独立保存；本轮可见内容仍取决于加载、快照时机、上下文预算和压缩，不能称作模型认知完全免疫压缩。

    查看解释与参考资料

    磁盘保存不代表模型始终看见完整文件；上下文文件可扫描、截断，记忆快照在本会话中也不会因后续写入自动刷新。

    Hermes Context Files：Loading and limits ↗

    每次会话重新从磁盘读，不进 .jsonl → 免疫 Compaction

  • 更正：分别核对项目上下文文件与内置记忆的预算；不要沿用 OpenClaw 的单文件和总字符数作为 Hermes 默认值。

    查看解释与参考资料

    20K/150K 的一组固定总预算没有 Hermes 官方依据。当前项目上下文上限可由 context_file_max_chars 指定，否则按模型动态缩放；内置记忆又有独立小预算。

    Hermes Context Files：Size Limits ↗

    字符限制：单文件 20,000 字符，总计 150,000 字符，超出截断

  • 更正：为子任务明确提供必要目标和上下文，并依据实际委派实现确认加载内容；不要假定它自动继承五份固定身份文件。

    查看解释与参考资料

    此五文件继承清单缺少 Hermes 版本依据。官方委派说明强调子任务独立上下文及限制的工具权限，不能由主会话文件列表推出可见内容。

    Hermes Subagent Delegation ↗

    子 Agent 只收到 AGENTS.md / SOUL.md / TOOLS.md / IDENTITY.md / USER.md，拿不到 MEMORY.md / HEARTBEAT.md
  • 用 /context list 查看注入状态
  • 尽量精简——每轮都占空间

7.3.3.2 memory/ 笔记

定位：Agent 的"事实性知识库"，不自动注入，靠工具按需检索。

更正：内置事实与用户记忆的文档路径为所用 Hermes home/profile 下的 memories/MEMORY.md 和 USER.md；其他记忆目录需注明外部插件或自定义来源。

查看解释与参考资料

此 memory/ 路径和接下来的默认检索工具不符合当前官方内置记忆说明。

Hermes Persistent Memory ↗

查看更正前的原段落

位置：/.hermes/memory/*.md、/.hermes/memory/**/*.md。

  • 文件命名一般是 YYYY-MM-DD-slug.md（归档） 或 topic.md（常青）
  • 写入来源：用户手写 / 会话结束时自动归档 / 自进化反思产出
  • 这些文件被 Retrieval Index 建索引，通过 memory_search + memory_get 被检索到

与 Bootstrap 的区别：Bootstrap 是"每轮都读"，memory/ 是"需要时才读"。


7.3.3.3 Skill Library

更正：下次相关任务可按需加载已有步骤，减少重复摸索；执行前仍需确认适用条件，执行后仍需验证结果。

查看解释与参考资料

Skill 提供可复用步骤，不保证机械执行即可成功，也不免除模型根据输入、环境和工具结果进行判断。

Hermes Skills System：Progressive Disclosure ↗

定位：把"成功完成过的流程"固化成可执行 skill，下次遇到类似任务直接调用，不用从零推理。

Skill 文件结构：

skills/<category>/<skill_name>/
├── SKILL.md          # skill 描述 + 触发条件 + 步骤说明
├── scripts/          # 可执行脚本（可选）
└── templates/        # 模板文件（可选）

目录分类（仓库 hermes-agent/skills/ 自带几百个预置 skill）：

skills/
├── software-development/   # 代码评审、重构、测试
├── research/               # 论文检索、总结
├── creative/               # ASCII art、Excalidraw
├── productivity/           # PowerPoint、邮件
├── devops/                 # CI/CD、Docker
├── mcp/                    # MCP 集成
└── social-media/

Skill 的三种生成路径（写入时机见 11.4.1）：

  1. 系统预置：仓库自带几百个 skill，随 Hermes 一起分发

  1. 更正：用户可通过 Hermes 的 Skills Hub 或已支持来源安装技能；Agent Skills 规范描述文件格式，实际安装须给出具体来源与标识。

    查看解释与参考资料

    agentskills.io 是开放格式与规范站点，不能把“从开放标准安装”当作具体技能来源。

    Agent Skills Overview ↗

    用户安装：/skills 命令或从 agentskills.io 开放标准安装
  1. Agent 自动生成：自进化闭环触发自动写 SKILL.md（如 Hacker News 每日简报的例子）

◦
对应：Skill Library
◦

对应：Honcho User Model
