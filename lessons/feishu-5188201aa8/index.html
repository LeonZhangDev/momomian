本课机制与检查方向

先用这个入门例子理解流程，再看下方完整讲解。

按本课演唱会工具调用示例，若恰好一次工具调用，访问模型服务通常有几轮？ 结论：两轮：先获工具请求，再提交工具结果生成答复。 理由：第一轮模型决定工具和参数，程序执行工具，再带结果进行第二轮模型请求，这里数的是模型交互，搜索工具自身可能另有网络请求，不能说中间必然无网络。 配套示例：模型→search_concert指令，工具返回结果，再模型→最终回答，模型调用共两次。 按本课提到的 Jaccard 集合重合度，假设标准参会人集合为 {甲,乙}，预测集合为 {甲,丙}，相似度是多少？ 结论：1/3。 理由：本站用具体集合计算，交集是{甲}，并集是{甲,乙,丙}，交并比为1/3，能同时反映漏掉乙与多报丙，而非只检查有无一个正确人。 配套示例：intersection大小1，union大小3，所以Jaccard=1÷3。

针对‘周杰伦演唱会’这个例子，如果 Function Call 正常工作，一共发生了两轮完整的 HTTP 交互。

◦
第一轮交互（意图识别）：Semantic Kernel 把用户问题发给 LLM。LLM 分析后，返回了一个 tool_calls 指令，告诉框架‘我要调用 search_concert 工具，参数是周杰伦’。此时 LLM 并没有生成最终答案，而是处于挂起状态。
◦
中间处理（本地执行）：框架拦截到这个指令，在本地运行了搜索代码，拿到了‘2025年3月2日海口站’这个结果。
◦
第二轮交互（结果生成）：框架把‘用户问题’、‘模型的调用请求’以及‘工具的运行结果’打包在一起，再次发给 LLM。LLM 看到工具返回的具体时间后，才生成了最终的自然语言回复：‘周杰伦的演唱会是在2025年3月2日’。

（如果你弄不明白上面的过程，请看这个更详细的解析）

第一轮交互：意图识别与工具选择

目的：模型分析用户问题，决定是否需要调用工具，以及调用哪个工具。

Request (SK -> LLM)

SK 将用户问题和所有可用工具的定义（Schema）打包发给模型。

Response (LLM -> SK)

模型识别出需要搜索，返回一个结构化的 tool_calls 指令。注意此时 content 通常为空或为 null。

工具请求，还不是执行结果

把一次工具调用分成三件事：模型提议、应用检查、工具执行。

阶段你会看到什么下一步
模型返回tool_calls 中的工具名、调用 ID 和字符串参数解析 JSON，并检查字段和权限
应用检查允许的工具与符合要求的参数执行工具并等待真实结果
工具返回成功结果，或明确的错误/未知状态按调用 ID 回传给模型

代入一个例子：模型提出 search({"query":"退款规则"})，只说明它想查询。只有检索程序实际返回片段后，才有可用的查询结果。

HTTP 200 表示请求层成功，finish_reason=tool_calls 表示模型提出工具调用；两者都不能证明工具已经执行。

更正：执行工具不增加一次模型请求，但工具自身可能访问网络。应分别统计模型调用、工具调用和底层 HTTP 请求。

这一步不产生网络流量。

SK 收到 finish_reason: tool_calls。
b.

第二轮交互：提交结果与生成回答

目的：将工具查到的结果喂回给模型，让模型生成最终给用户的自然语言回复。

Request (SK -> LLM)

SK 构造一个新的请求，包含完整的历史上下文：

a.
用户的原始问题。
b.
模型上一轮的“我想调工具”的请求（Assistant Message）。
c.
工具实际运行的结果（Tool Message）。

让工具结果找到对应请求

请求和结果靠调用 ID 配对，不能只按消息顺序猜。

消息必须保留的联系
assistant 的工具请求工具名、参数与 tool_call ID
tool 返回用 tool_call_id 指向对应请求，content 放实际结果
模型继续回答同时参考原请求与对应结果，说明失败或缺少证据的情况

代入一个例子：同一轮请求 call_a 查订单、call_b 查库存。库存先回来，也要标 call_b，不能把它贴给订单查询。

这里只解释关联规则，完整请求格式要按实际接口核对。保留消息不等于参数、权限或执行结果已经通过检查。

Response (LLM -> SK)

Response API 是Openai设计LLM调用接口的从 Completions → Chat Completions → Responses 的过渡：早期的 Completions 只面向纯文本续写；随后 Chat Completions 围绕 messages 支持对话与函数调用，但状态与工具编排仍主要在客户端；如今 Responses 用一个 有状态的统一端点把多轮上下文与多步工具调用纳入服务端协议。

更正：Responses 可以编排托管工具；自定义函数通常由应用读取调用参数、执行函数，再提交结果继续响应。是否需要客户端循环取决于所用工具和接入方式。

托管工具与自定义函数的执行方不同，不能概括为外部工具都由单次响应自动执行。

设计思想与理念：以 “一次请求里的智能体循环” 为核心，把 状态、工具、事件流与结构化输出 写进端点契约（而非让客户端手工拼装），让模型在单次响应生命周期中 按需调用托管/外部工具、跟踪步骤并输出可验证结果，从而标准化智能体能力、降低工程胶水、提升可观测与可扩展性。
